## Context

A user requested a fix for both failing jobs in the `Validate source checkout` GitHub workflow,
in a separate worktree and branch. The primary invocation omitted `target_id`, selected
`specify:false`, and left reviews enabled. The host created a candidate from committed base
`2c398af9af2510768d945c7cde7da5a57ff8fcfd` and returned a P10 session handoff before discovery.

The candidate was `change.499465ba-0619-431f-9220-063b7dd5d8da`, on branch
`concorde/499465ba-0619-431f-9220-063b7dd5d8da`. Its initial state legitimately had
`target_id:null`, an empty target map, and phase `created`. A fresh session resumed the same
change with its `change_id`, without inventing an owning Module.

This record owns the Development resume defect and captures the related orchestration questions
found while investigating it. Harness owns worktree state and binding; Spec owns implementation
context expansion. Those participating responsibilities require separate contract contexts if
their behavior changes. No dev-loop implementation fix has been applied by recording this issue.

## Expected

Creating a candidate and binding its target are distinct lifecycle events. A legitimate P10
handoff before routing must be resumable without a supplied target. The host should use the
persisted binding and trusted routing evidence to decide which stage remains, not the mere
presence of a request `change_id`.

An unbound candidate should continue discovery and target selection. A bound candidate should
retain its recorded owner and reject incompatible changes to task, focus, constraints, or target.
Malformed or inconsistent recovery inputs should produce a structured diagnostic, not a Python
key lookup exception. A caller's routing hint must not become a write grant.

If discovery or subsequent assessment establishes a missing contract or implementation binding,
the result should distinguish that repairable gap from an execution failure. The candidate and
original task should survive with an actionable recovery identity. Existing Spec authoring,
topology application, and candidate validation have different authority and must not be conflated.

Final validation and readiness should continue using the current candidate's Spec and evidence.
An explicit Git maintenance merge is a separate operation; it must not be represented as a
successful dev-loop, a ready candidate, or a normal delivery receipt.

## Observed

### Direct failure before the dev-loop graph

`run_capability()` invokes `_worktree()` before `_dispatch()`. On the primary worktree,
`create_worktree()` and `ensure_change()` initialize the candidate without a target. The host
returns `worktree_handoff_required` before `MainInvocation.select_one()` runs.

On resume, `_dispatch()` routes a main-routed capability only when the request does not contain
`change_id`. It therefore skips routing for this valid unbound candidate. It then calls
`bind_owner()`, which reads `task["target_id"]` while the stored owner is empty. The generic
exception handler converts the resulting `KeyError` to `execution_failed` with message
`'target_id'`. No Spec author, planner, implementation Agent, or validation node has run.

An in-memory probe extracted the actual `_dispatch()` and `bind_owner()` functions from both
the incident baseline and the then-current checkout, replacing routing, graph construction, and
state writes with observable substitutes. All four combinations of baseline/current and
`specify:false`/`specify:true` raised the same `KeyError`, with no routing, graph, or write event.
This is a focused control-flow reproduction, not an end-to-end capability execution.

### Independent ownership question and maintenance repair

After the exception, a separate `concorde-main` request with `action:ask` reported
`spec_incomplete` because the selected Module declarations did not bind the workflow. This was
an independent question, not a dev-loop routing result or a final validation failure. The initial
explanation to the user incorrectly treated these events as one causal chain and attributed the
first exception to `specify:false`.

Inspection of all registry and entity declarations at the baseline, CI repair commit, and current
checkout confirmed that `.github/workflows/validate-source-checkout.yml` had no binding, while
`tests/concorde/harness/test_studio_server.py` was bound by `module.harness`. This is a real
implementation-binding gap; it does not establish that a responsibility cannot be routed or that
every implementation file must have an exclusive owner. Shared file bindings are supported.

A separate authorized maintenance session fixed CI, tested it, performed an independent read-only
review, and committed `22251f493066546223918acbb1fc473a07c87cb4`. It did not register those external
results as lifecycle evidence. Normal delivery subsequently returned `incomplete_change` before
integration because the candidate lacked ready state and `validated_tree`.

### Existing mechanisms and remaining design questions

Final validation already reloads the current candidate repository. Authoring applies and validates
replacement documents; subsequent graph stages construct fresh contexts. Review uses the base
commit to derive the diff, while the current complete Module Spec supplies the contract. Changing
validation from an original Spec to a candidate Spec is therefore not the required fix.

Ordinary `specify` can replace registered documents but cannot add or remove file bindings.
Existing `design-topology`, `accept-topology`, and `apply-topology` operations can change registry
entries and Module entity declarations together. However, dev-loop lacks a recoverable connection
to that path: the current contract permits only the automatic code-review-to-tasks revision edge.
Moreover, `_apply_topology()` binds the change to the registry's entry target, which is not a safe
drop-in transition for an existing single-target development task.

There is also an existing formal `validate` path for direct maintenance candidates without authored
targets. It can run configured checks and record direct-candidate evidence. That path was not
attempted for this candidate. Consequently, the incident does not prove that maintenance candidates
can never become ready or that a manual merge was the only possible recovery. Its actual admission
and applicability must be checked, rather than assumed from external passing logs.

The investigation found a related boundary ambiguity: P5 broadly describes exclusion of dot-prefixed
paths, while `expand_entry()` accepts an explicit `.github/workflows/validate-source-checkout.yml`
entry and an explicit `.github/workflows/` directory entry. The existing recursive exclusion is not
uniformly applied to explicit roots. This needs a separate Spec/implementation reconciliation if
workflow bindings become part of the repair; neither blanket prohibition nor implicit permission
should be inferred from this observation.

Two attempts to launch a standard source review stopped with `incompatible_handoff`, reporting
`main route changed single-target task intent`. They did not start a reviewer. Exact preservation
of task and constraints is currently required; without the original route payloads, these responses
are not evidence of another Python implementation bug. Field-level diagnostics and host retention
of immutable request intent are candidate improvements recorded in the attached investigation.

## Impact

A valid host-created candidate can be stranded before its first bounded Agent executes. Selecting
`specify:true` does not recover it, and supplying an invented target would risk bypassing the very
discovery and authority boundaries the host is supposed to establish.

The error hides the unfinished routing stage behind an unhelpful field name. This encourages an
outer agent to misdiagnose a Spec gap, switch to maintenance, and leave code completion disconnected
from lifecycle evidence. In this incident the CI fix was independently tested and committed, but
normal delivery remained blocked and the user ultimately authorized an explicit Git merge exception.

The resume bug should be repaired separately from a broader topology-recovery design. Merely removing
ready checks, widening a writer's scope, accepting caller hints as ownership, or rewriting lifecycle
records would not repair the cause and would undermine existing guarantees.
