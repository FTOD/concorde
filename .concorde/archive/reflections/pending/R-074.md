# R-074 · Task authors assign provider workers verification they cannot perform

## Context

In the coordinated change `change.8325c8c8-747e-48e9-b06e-ccd226365307`, both the root Module and
Development, acting as coordinators, produced component tasks whose acceptance required a
provider-bound worker to inspect or verify another Module's declarations:

- Development's task for Harness read "In a fresh module.harness context, establish and verify
  Development's required contract.harness.graph-admission and local Harness dependency promises
  ...". The Harness Spec author, bounded by P5 to Harness's own collection, could only record gap
  `2e2ae806…`: "Only the provider declaration and consumer scenario IDs are supplied here."
- An earlier Development task for Harness named `scenario.development.shared-graph-admission`,
  `shared-graph-rejection` and `shared-graph-policy` as acceptance without carrying their content;
  Harness recorded gap `65fe0905…` asking what those scenarios require.
- The root task for Distribution asked it to validate registrations "against Development's
  capability registry and Harness's execution surface" although Distribution declares no Harness
  dependency; Distribution recorded gap `d0c74f0f…` asking whether a Harness surface exists that it
  must validate.

Each of these gaps cost a human round trip: a developer-authorized Spec repair that restated the
missing fact locally, followed by a fresh run of the loop, before the provider's assessment could
complete.

## Expected

A task assigned to a used Module or child is satisfiable from that Module's own complete
collection and its phase grant. Verifying that a consumer's required declaration matches a
provider's provided declaration is the consumer's task or deterministic validation's job
(`CONCORDE-CONTRACT-001..003`), never a provider worker's. Acceptance that cites another Module's
scenario identifiers carries the relied-upon promise text in the coordinator's own local dependency
declaration, so the provider can read it. A coordinator's plan does not invent surfaces that the
component's registered dependencies do not contain.

## Observed

- `agents/spec_engineer/modes/tasks.md` tells the task author that a task may target "a direct
  submodule or a declared dependency" and to "use only locally specified stable IDs,
  responsibilities, selection conditions and relied-upon promises", but it does not say that a
  component task must be completable from the component's own collection, nor that cross-Module
  agreement checks belong to the consumer or to deterministic validation.
- The host admits any component task whose `target_id` is a declared dependency or child; it does
  not check whether the acceptance text references identifiers foreign to that component.
- Provider workers behave correctly under P5: they stop and report a gap instead of reading the
  consumer's collection. The cost is therefore paid in whole loop iterations rather than being
  prevented at task authoring.

## Impact

Nested coordination (root → Development → Harness/Distribution/Reflections/Spec) multiplied the
effect: three of the loop's stops in this change were caused by unsatisfiable provider tasks rather
than by real contract gaps. Every such stop requires a human to restate, inside the provider's own
collection, a fact the coordinator already possessed.

## Evidence

- Gap `2e2ae806…` and the Development component task text for `module.harness` in
  `/tmp/concorde-worktree-o6t40205/project/.concorde/worktree.json`
  (`targets.module.development.coordination.module.harness.task`), recorded on 2026-09-11.
- Gap `65fe0905…` (same file, earlier Development task text) and gap `d0c74f0f…` (root
  coordination, Distribution task text mentioning "Harness's execution surface").
- `agents/spec_engineer/modes/tasks.md` at `569ac7ba`: the targeting and ID rules quoted above;
  `src/concorde/development/capability_host.py#implement_scope`: the component admission check
  (`coordinated task must name a declared dependency or direct submodule`).
- Developer repairs that unblocked each case, all inside the candidate of change `8325c8c8`:
  Development's "Graph ownership" paragraph and Harness promises (`specs/concorde/development/
  module.md`), the `contract.harness.graph-admission` blocks on both sides, Distribution's
  Development dependency promises (`specs/concorde/distribution/module.md`) and the provider-side
  verification sentence in `specs/concorde/harness/host.md`.

Candidate directions, for triage rather than decided here:

- Extend the tasks-mode instructions: a task assigned to another Module must be satisfiable from
  that Module's own collection; consumer-side agreement checks are the consumer's own tasks;
  acceptance that names another Module's scenario carries the relied-upon promise text.
- Have the host reject or flag a component task whose acceptance references scenario, requirement
  or contract identifiers that the component's collection does not define, before dispatching it.
- Let coordinators hand a component the relied-upon promises from their own local dependency
  declaration as an explicit stage input, so the provider sees the consumer's expectation without
  reading the consumer's collection.
