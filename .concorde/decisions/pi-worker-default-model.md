# Decision log: pi-worker-default-model

Goal: A pi worker whose worker configuration names no model runs on the developer's own pi default (defaultProvider, defaultModel, defaultThinkingLevel of their pi settings) instead of pi's built-in default

## Brief (main agent `claude session stuck debug`, 2026-09-29)

Origin: the main session `clear-conversation-state` found in a live pi verification
(`/tmp/concorde-e2e/verify-pi`) that without `.concorde/workers.json` a pi worker ran on pi's
built-in default model (`anthropic/claude-opus-4-8`), not the developer's pi default
(`local-openai/gpt-6`). The developer approved handling it at 2026-09-29T06:34Z ("第4点也一起处理").
Deferred until the overlapping tasks `owner-only-wake` and `tracing` merged; both have.

Cause: `src/concorde/harness/pi_backend.py` (`_configure`, around lines 348-362) copies only
`auth.json` and `models.json` from `~/.pi/agent` into the worker's runtime directory and writes a
`settings.json` holding only `{"defaultProjectTrust": "never"}`, so pi falls back to its built-in
default.

Decided by the main agent without the developer (ordinary scope; it makes the existing promise
"pi's default model" mean what the developer sees as pi's default): the worker's generated pi
settings inherit `defaultProvider`, `defaultModel` and `defaultThinkingLevel` from the developer's
pi settings (`~/.pi/agent/settings.json`, or pi's agent directory as pi resolves it) when they
are set, keep `defaultProjectTrust: "never"`, and copy nothing else (no extensions, packages or
other settings). A backend, model or reasoning level set in the worker configuration still wins
field by field. A missing or unreadable settings file leaves pi's built-in default, as now; a
malformed one is a detailed error, not a silent fallback. State this precisely in the Workers Spec
(module.workers) and cover it with deterministic tests.

Left to the session: code shape, test placement, Spec wording.

## Task session decisions (2026-09-29)

- **Code shape.** `user_defaults(path)` in `src/concorde/harness/pi_backend.py` reads the user's pi
  `settings.json` and returns only `defaultProvider`, `defaultModel`, `defaultThinkingLevel`;
  `_configure` writes them with `defaultProjectTrust: "never"` (the trust setting always wins, even
  over one in the user's file). Precedence of the worker configuration needs no code: `--model` and
  `--thinking` on pi's command line override its settings field by field.
- **What counts as malformed** (refused with the new code `pi_settings_invalid`, reason
  `environment`, detail naming the file, the problem and how to repair it): not UTF-8, not JSON
  (with line and column), a JSON value that is not an object, one of the three fields not a
  non-empty string, or `defaultThinkingLevel` outside pi's levels (the same fixed vocabulary the
  worker configuration validator uses, `models.LEVELS["pi"]`). Mirroring pi: a UTF-8 BOM is
  stripped and an empty file means no settings. "Missing or unreadable" = the read raises `OSError`
  (absent file, permission denied, a directory in its place): nothing inherited.
- **Agent directory resolution** now expands a leading `~` in `PI_CODING_AGENT_DIR`, as pi's own
  `getAgentDir` does; before, such a value was taken literally for `auth.json`/`models.json` too.
- **Spec**: `pi.md` (run directory paragraph, error row, new `req.workers.pi-user-default`),
  `launch.md` error row, `module.md` "the program's own default" sentence, two new scenarios
  `scenario.workers.pi-user-default` and `scenario.workers.pi-settings-invalid` in `scenarios.md`,
  verified by deterministic tests in `tests/concorde/harness/workers/test_pi.py`.
- **Not done, noted for the main agent**: pi's `modelThinkingLevels` (per-model startup levels) and
  `enabledModels` also influence pi's startup choice; per the brief ("copy nothing else") they are
  not inherited, so a developer who relies on `modelThinkingLevels` instead of
  `defaultThinkingLevel` gets `medium` in the worker. The main-session skill's sentence "every
  worker runs on pi with pi's default model" (module.main-session, outside this task) stays true in
  meaning and was not changed.
- **Verification.** Full suite 795 passed / 4 skipped; `build --check` and `spec-validation` ok;
  `task-validation` ready with no blocking findings. Live check: a runtime directory generated by
  `_configure` from the developer's `~/.pi/agent` made `pi -p` start on `local-openai/gpt-6` at
  `high` (the session's `thinking_level_change` and each `message_end` name them). The model call
  itself ended `Connection error.` because the local-openai endpoint is not reachable from this
  session's sandbox, which does not affect which model pi chose.
- **Delivered** as `ea866d2a` (evidence `.concorde/evidence/pi-worker-default-model/1.json`).
