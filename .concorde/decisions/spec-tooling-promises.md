# Decision log: spec-tooling-promises

Goal: Developer-approved panel-review decisions for Spec tooling: (spec F6) narrow the freshness claims of validation.md 'What success means' and req.spec.digest-per-assessment to what source_digest covers, saying findings about bindings and coverage can change without it; (spec F26) limit the file transaction's all-or-nothing guarantee to failures the process observes and state what an interruption or failed restore leaves; (spec F28) restate init --apply's guarantee as shape, digest integrity, freshness, allowed files and a validating result, not provenance; (spec F8) wrap OS errors from a transaction's writes or rollback into a SpecError with a system_error cause, documenting that a verify callback's own exception propagates unchanged; (views F2) add docsite/site.json to the docsite source digest in model.ts; (concept.spec-context) redefine it in the glossary and vocabulary.md as the Protocol's SpecContext of the bound Modules (plus terms) without ExternalContext, as every other text uses it; (spec-mcp F11) record the rationale the developer accepted: a hand-written JSON-RPC session keeps Spec MCP free of a runtime dependency for a small, fully specified wire, and CLAUDE_PROJECT_DIR wins over the client's roots because it is the project directory Claude Code sets while roots may be several. ## Decisions (task session, 2026-09-29)

1. **F6, what the validation digest leaves out.** Named exactly what `source_digest` does not cover, read from `validate_repository`: the files Modules bind, the list of version-controlled files (`CHK.binds.unbound`) and the tests scanned for verification declarations. Stated in validation.md "What success means", as an explanation under `req.spec.digest-per-assessment` (the SHALL sentence unchanged), and in contracts.md's validation result. Options: widen the digest to cover them (a behaviour change the goal did not ask for) or narrow the claim (the goal). Chose narrowing.
2. **F26/F8, error codes of a failed transaction.** Both a refused write and a refused restore raise a `SpecError` with code `system_error` (no new code), with call-site reasons and remediations; the refused write carries one `system_error` cause, the refused restore carries the first failure (unchanged when a SpecError, else its system_error/unexpected_error record) plus one cause per refused restore. Other restores are still attempted. Alternative: a new code such as `write_failed`/`partial_rollback`; rejected as unnecessary vocabulary since the registered `system_error` reason fits.
3. **F8, an OSError raised by `verify` is not wrapped.** Only OS errors of the transaction's own writes are wrapped; any exception from the caller's `verify` (including an OSError) propagates unchanged once files are restored, as the goal says. Only a refused restore changes that, because the partial state must be reported.
4. **F26, interruption.** Kept `except Exception` (a KeyboardInterrupt/SystemExit or kill restores nothing) and documented it, rather than catching BaseException, since the goal asks to limit the guarantee to failures the process observes, not to widen restoration.
5. **F26/F8 Spec shape.** Added `req.spec.transaction-restore-reported`, `req.spec.transaction-system-errors` and scenarios `transaction-write-refused`, `transaction-restore-refused`, `transaction-check-error`, each verified in tests/concorde/spec/test_file_transactions.py. Narrowed the glossary definition of `concept.file-transaction` (owned by module.spec) to match. Updated tests/concorde/views/test_scaffold_creation.py, which expected a raw OSError.
6. **F28.** Kept the requirement identity `req.spec.init-explicit-envelope` and retitled it "Apply checks shape, integrity and freshness"; the statement no longer claims the proposal came from propose. Left Distribution's module.md sentence "`concorde init --apply --proposal <file>` applies exactly the proposal it printed" unchanged: it is usage wording in module.distribution, outside this task's Modules, and does not claim enforcement.
7. **Views F2.** `docsite/site.json` is appended last to the docsite source digest only when it exists (read through `safeRead`, so a symlink is refused); a project without it keeps working as before. Two tests (`adds collection and executable tabs…`, `a consumer adds a separate docs tab…`) asserted the model/manifest unchanged after a site.json edit; they now assert only the source digest moves. pipeline.md and views module.md name the new input.
8. **concept.spec-context.** "vocabulary.md" no longer exists (renamed to core-concepts.md in fb79b169); redefined the term there and in the glossary. Core concepts now says ExternalContext is a separate read set every task type grants beside the Spec context. Open point, not changed: `concept.context` still defines a worker's context as the union of four kinds, none of which now names ExternalContext.
9. **Spec MCP F11.** Recorded both rationales in spec-mcp/module.md Design, naming the actual wire (newline-delimited JSON-RPC: initialize, ping, tools/list, tools/call, one roots/list request).
