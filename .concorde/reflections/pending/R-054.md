# R-054 · Context selection and bounded task execution share one ambient cognition

## Context

Profile 8 introduces an Operation host that resolves one target's complete Spec collection and
starts a fresh bounded worker process. Public Skills are still invoked by the agent in the user's
ambient conversation. Two public deterministic Operations, `concorde-context` and
`concorde-resolve-context`, return the resolved snapshot to that ambient caller. The snapshot embeds
the selected Markdown bodies and the global Protocol/kind bodies, not only their identities.

There are two distinct responsibilities in this flow. A project-level coordinator needs enough
global knowledge to understand the user's intent, identify the uniquely relevant target and create
the task/context request. A target worker must then perform the requested work using only the chosen
snapshot. These responsibilities require different cognition sessions because information already
seen by a model cannot be removed by later filesystem restrictions.

## Expected

The main coordinating agent has an explicitly defined global project view sufficient to select one
target and construct a bounded request. After selection, a different, fresh worker agent receives
the resolved target context and performs the task. The coordinator does not continue as the worker,
and the worker does not inherit the coordinator's transcript, other target bodies or arbitrary tool
outputs. The handoff identifies the selected target, task, constraints and context identity through
a declared contract.

The global coordinator is a separate role from a target-local reader. The current
`concorde-ask` surface is the closest existing coordination concept, but its present implementation
is itself bound to one already selected target and therefore does not yet define the required global
selection responsibility.

## Observed

`resolve_context` places every admitted document's `content` in the snapshot. `_dispatch` returns
that complete snapshot from both public context Operations. Their projected public Skills instruct
the ambient agent to invoke the executable and report its result. Consequently, the same ambient
agent can resolve target A, retain A's full body in its conversation, resolve target B, retain B's
full body, and then reason or act using both even though every inner worker launch is fresh.

The current architecture protects the nested worker process but does not establish a cognitive
boundary around the agent that selects and invokes that process. It also does not define the
authorized global context from which target selection is made.

## Impact

The central guarantee that one task has one unique Spec context is not end-to-end. It depends on the
ambient agent voluntarily ignoring information it has already received. Target changes can silently
accumulate Spec bodies in one conversation, and a later answer or implementation request cannot prove
that only the latest collection influenced the result. Making snapshot files unreadable afterward
does not repair the prior cognitive input.

The unresolved architecture question is the exact content and authority of the main agent's global
view, together with the typed handoff that separates selection from bounded execution without giving
the worker access to the global view.

## Evidence

- `src/concorde/specification/context.py#resolve_context` embeds `documents[].content` and
  `protocol[].content` in `concorde-context-snapshot`.
- `src/concorde/capabilities/scoped_operations.py#_dispatch` returns that snapshot from the two
  public context Operations.
- `.agents/skills/concorde-context/SKILL.md` exposes the resolver as an ambient public Skill.
- Reproduction at `d3ad1eb`: invoking `operations/concorde-context/operation.py` for
  `domain.installation` returned the complete Domain document and Protocol bodies on stdout.
- `protocol/principles.md` P5 and P7 prohibit undeclared predecessor context and require a fresh
  context when the target changes.
