# R-055 · Deterministic checks execute outside their declared authority

## Context

Profile 8 allows each target to register deterministic checks. A check record contains an ID,
owning target, argv, timeout and optional `inputs`. The workflow treats check results as trusted
implementation evidence while withholding raw logs from later Spec-only agents. The Protocol also
states that deterministic tools may inspect separately authorized code but must not become an
arbitrary read or command proxy.

This review examined whether the registered `inputs` and the target's implementation ownership are
execution permissions or only evidence metadata.

## Expected

A deterministic check runs with host-issued authority limited to its declared inputs and intended
outputs. Its filesystem reads and writes, command execution, environment, network and credentials
are bounded independently from the agent. Project-authored runtime data cannot widen that authority.
A check that attempts to read a secret, write outside its declared result area, change unrelated
implementation or access the network is prevented by the host rather than merely detected after the
command exits.

The returned status and digests may cross into workflow state, while raw output remains available
only through an explicitly authorized implementation investigation.

## Observed

Registry admission accepts any nonempty string-array `argv` and validates `inputs` only as safe
project-relative path strings. `_check_revision` hashes those inputs, but `_check` passes the argv
directly to `subprocess.run` in the project root. The subprocess inherits the complete host
`os.environ`; no filesystem, process, network or credential sandbox is applied.

After execution, the host re-hashes the selected target's implementation and check inputs. This can
detect some mutations to those exact paths, but it neither prevents the command from reading them nor
detects reads, network effects or writes elsewhere. A detected mutation is also not rolled back.

## Impact

A mutable project registry can turn validation into a host-privileged arbitrary command. The check
can read credentials, transmit data, create or modify files outside the target, start child processes
or perform other effects while still returning exit code zero. The agent sandbox therefore does not
establish the task boundary claimed by P7 because a deterministic stage has a broader untracked path.

This is deferred as a recorded permission defect. No runtime correction is included with this
reflection.

## Evidence

- `src/concorde/specification/repository.py:197-209` admits arbitrary argv and records optional input
  paths without compiling a permission policy.
- `src/concorde/capabilities/scoped_operations.py:125-150` invokes the command with full
  `os.environ` and no sandbox.
- Executable reproduction against the branch consumer fixture replaced `check.transfer` with a
  Python argv whose only declared input was `app/transfer.py`. The command read the deliberately set
  environment value `CONCORDE_REVIEW_SECRET=sentinel` and wrote `outside-authority.txt`. The Operation
  returned `status=succeeded` and the check returned `status=passed`.
- `protocol/principles.md` P7 requires deterministic tools to read separately authorized code and
  forbids a broader arbitrary command proxy.

## User Comments

The maintainer requested that this problem be recorded as a Reflection and not fixed in the current
change.

On 2026-09-06 the maintainer clarified the current boundary: checks do not need a more restrictive
read or command permission model yet. They may read project files and create temporary files in
host-managed temporary space, but they must not create, modify, move or delete any file inside the
project. Detailed check permission management is deferred; keep this Reflection open.
