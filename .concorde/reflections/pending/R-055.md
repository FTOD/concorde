# R-055 · Configured checks can mutate project files

## Context

Profile 11 registers deterministic checks with an ID, owning Module, argv, timeout and optional
input paths. The host runs these checks as implementation evidence and keeps their raw output out
of Spec-only agent inputs.

The maintainer narrowed this reflection on 2026-09-06: checks may read project files and create
temporary files in host-managed temporary space, but must not create, modify, move or delete files
inside the project. More detailed read, command, environment, network and credential permissions
remain deferred.

## Expected

The host prevents configured check processes from changing any project file, including temporary
changes that are undone before exit. Checks can use host-managed temporary space outside the
project. Host-owned persistence of logs and lifecycle evidence is separate from the check process's
authority.

## Observed

`_check` in `src/concorde/development/capability_host.py` invokes configured argv with
`subprocess.run` in the project root. No project read-only enforcement is applied.
Setting `PYTHONDONTWRITEBYTECODE` suppresses ordinary Python bytecode output but does not prevent
other writes.

`_check_revision` compares the selected Module's implementation and declared check inputs before
and after execution. A detected change raises `stale_evidence`, but the mutation has already
occurred and is not rolled back.

Current validation adds broader detection: with a candidate work directory it compares the
deliverable tree; it also rechecks affected Module revisions. These comparisons can reject
persistent changes missed by an individual check's digest. They do not prevent writes, and restoring
original bytes before comparison can conceal a write that violated the maintainer's boundary.
The deliverable snapshot excludes local lifecycle paths and is not a record of all filesystem
effects.

## Impact

A configured check can alter or remove project files before the host rejects its evidence.
An individual check can report `passed` after changing unlisted files, and a temporary write
followed by restoration can pass the byte comparisons. Passing checks therefore do not establish
that execution left project files untouched throughout the run.

This remains a project-write permission defect. Broader restrictions on reads, commands,
environment, network and credentials are outside its current scope.

## Evidence

- Revalidated on 2026-09-10 at `5277d68238335869005204714d4db2145820bfea`.
- `src/concorde/spec/repository.py#SpecRepository._load_registry` admits registered argv and
  input metadata.
- `src/concorde/development/capability_host.py#_check_revision` and `#_check` hash selected
  inputs, run the subprocess without project read-only enforcement and detect some changes
  afterward without restoring them.
- `src/concorde/development/capability_host.py#Invocation.validate` adds candidate-tree and
  affected-Module checks; `src/concorde/harness/change_worktree.py#snapshot_tree` captures final
  deliverable bytes, not a history of filesystem effects.
- A temporary consumer-fixture probe using `tests/concorde/spec/support.py#project` directly
  invoked `_check` with `inputs=["app/transfer.py"]`. Creating, modifying, moving and deleting
  unlisted project files each returned `passed`. A persistent change to `app/transfer.py` raised
  `stale_evidence` and remained on disk; changing it and restoring its original bytes returned
  `passed`. Writing in host temporary space also passed, as allowed by the maintainer. These are
  individual runner results, not successful full candidate-validation receipts.
- `BoundaryTests.test_separate_check_inputs_invalidate_evidence` and
  `BoundaryTests.test_delivery_requires_real_current_checks` in
  `tests/concorde/harness/test_boundaries.py` both passed. They verify evidence freshness rather
  than prevention of project writes.
- `specs/concorde/development/interfaces.md` documents host-run checks and private logs; the
  no-project-writes scope above comes from the maintainer's clarification below.

## User Comments

The maintainer requested that this problem be recorded as a Reflection and not fixed in the current
change.

On 2026-09-06 the maintainer clarified the current boundary: checks do not need a more restrictive
read or command permission model yet. They may read project files and create temporary files in
host-managed temporary space, but they must not create, modify, move or delete any file inside the
project. Detailed check permission management is deferred; keep this Reflection open.
