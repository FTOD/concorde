# R-056 · Initialized Profile 8 projects have no bounded topology authoring path

## Context

`concorde-init` intentionally creates an honest one-document Domain stub. The README then instructs
the maintainer to supply business rules and register Services and Modules before implementation.
Normal architecture evolution can also require adding or removing a target, changing scope nesting,
changing component ownership, recording participation, adding a Markdown member, assigning code or
registering a check after the project already uses Profile 8.

This concern is distinct from how Concorde bootstraps a breaking change to its own Protocol. The
current Domain/Service/Module refactor is an explicitly authorized Protocol cutover and is not
expected to execute through the previous Protocol's lifecycle. The question here is what an already
initialized Profile 8 consumer project can do after the new Protocol is active.

## Expected

The active Protocol clearly identifies the authority and bounded process for changing a Profile 8
registry and its associated Spec document membership. A coordinated topology change has explicit
preconditions, reviewable proposed bytes, target and relationship validation, rollback on invalid
state and an auditable result. It must be possible to distinguish human-supplied business facts from
metadata that a deterministic host may validate.

## Observed

`concorde-specify`, `concorde-clarify` and `concorde-constitution` can return document replacements,
but the host allow-list is exactly the selected target's existing `documents`. Those Operations
cannot add a new document path or modify `.concorde/specs.json`.

`concorde-init` cannot run after configuration exists. `concorde-migrate` accepts an authored
registry, but it explicitly requires the current configuration to be Profile 7. `concorde-configure`
changes only the agent integration/enforcement setting. No other registered Operation owns a Profile
8 topology change.

## Impact

The initialized stub cannot reach the advertised multi-target model through a Concorde-defined
boundary. A maintainer must edit control metadata and create files manually or use an undeclared
external process. Ordinary later architecture changes have the same gap. That makes registry
authority less controlled than target-local prose, even though the registry determines context
membership, code ownership and check execution.

The reflection does not assert that the in-progress Protocol refactor should have been performed
under Profile 7. It records the missing steady-state behavior for projects after Profile 8 adoption.

## Evidence

- `src/concorde/capabilities/scoped_operations.py:255-267` applies author output only to
  `set(self.target.documents)`.
- `src/concorde/specification/initialize.py:25-55` creates only the initial Domain stub.
- `src/concorde/specification/initialize.py:58-80` rejects migration unless the current profile is 7.
- `src/concorde/capabilities/protocol_contracts.py` registers no Profile 8 topology-authoring request.
- `README.md` asks users to register Services/Modules after initialization without defining the
  corresponding authority boundary.

## User Comments

The maintainer clarified that a breaking Concorde Protocol change must first complete and then
validate the coherent new Protocol; the previous Protocol must not deadlock its own replacement.
That bootstrap decision is recorded separately in the project Constitution and does not by itself
answer this steady-state consumer-project question.

On 2026-09-06 the maintainer decided that system-structure design belongs to the global-view main
agent introduced by R-054, because that role has the broadest permitted understanding of the
Concorde Protocol and the project's Domain/Service model. The public `concorde-main` Operation must
replace `concorde-ask`, not coexist with it as an alias. Main may inspect exact registry topology,
all global kind definitions and any Domain/Service Specs admitted through discovery, but it still
must not inspect Module document bodies or implementation code.

The agreed mutation boundary separates design, authoring and application. Main first returns a
reviewable, digest-bound topology design without writes. Explicit maintainer acceptance starts fresh
target-local Spec authors; only the author for a Module may receive that Module's existing body. The
host validates their complete proposed document collections against the candidate registry without
changing project files and stores the exact result as an artifact. A second explicit maintainer
acceptance applies that exact artifact atomically. Main cognition receives only target-author typed
status/gaps and the artifact reference, never their full document output.
