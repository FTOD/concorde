# R-057 · Domain task authors cannot identify registered participants from their context

## Context

Profile 8 permits a Domain change to coordinate separately bounded component changes. A Domain task
author sees the Domain collection and must produce task records containing exact target IDs. The host
then verifies that each selected Service or Module participates in that Domain or a nested scope.
Relationship metadata is stored in `.concorde/specs.json` as component-side `participates_in` IDs.

Concorde's own Workflow, Installation and Publication Domains name participating concepts in prose,
such as the context Service, Operation host and package assets Module.

## Expected

The admitted Domain context contains enough local information to identify every component that the
Domain is allowed to coordinate. For each relevant participant it states the stable target ID, the
role played in this Domain, the interaction trigger and the promises the Domain relies on. The task
author can therefore emit an exact `target_id` without consulting the registry, another Spec,
implementation code, prior model memory or naming conventions.

If a participant identity or role is absent, context solving reports the specific Domain Spec gap
before task generation.

## Observed

`resolve_context` explicitly omits scope ancestry, component ancestry and participating targets.
The snapshot includes the selected target ID and kind, but no relationship inventory. The Domain
documents registered for `domain.workflow`, `domain.installation` and `domain.docsite` contain none
of their participants' stable IDs even though the registry records ten, seven and two participating
components respectively.

`concorde-task-author` requires every result to contain a target ID. The Domain coordination test
does not demonstrate that an agent can derive that ID from context: its callback overwrites the
model-double result with the literal `service.transfer`.

## Impact

A compliant Domain task author cannot route normal cross-component work. It must either return Spec
incomplete or guess an identifier from general knowledge. Guessing violates the no-search/no-memory
boundary; returning a gap means the advertised Domain coordination path is not usable with
Concorde's own current Domain collections.

The same omission prevents the Domain Spec from answering a key business-architecture question:
which exact entity owns a named responsibility in this scope.

## Evidence

- `src/concorde/specification/context.py:49-56` explicitly excludes participation and ancestry
  metadata from the snapshot.
- `.concorde/specs.json` contains participant IDs that are absent from the corresponding Domain
  Markdown collections.
- `src/concorde/capabilities/protocol_contracts.py:17-18` requires `target_id` on every task item.
- `skills/concorde-task-author/SKILL.md` allows Domain tasks to select explicitly described
  participants only.
- `tests/concorde/specification/test_scope_and_reflections.py:17-25` injects the participant ID from
  the model-double callback rather than deriving it from the supplied snapshot.

## User Comments

On 2026-09-06 the maintainer accepted all four resolution constraints: every Domain Spec explicitly
lists each relevant participant's stable ID, kind, Domain-local responsibility, selection condition
and relied-upon promises; deterministic validation compares those declarations with registry
`participates_in` relationships; a missing declaration becomes a structured Spec gap during context
solving; and the R-056 topology workflow is the authorized way to reconcile the registry and affected
Domain collections together.
