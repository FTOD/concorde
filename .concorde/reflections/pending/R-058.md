# R-058 · Shared physical Spec members couple independent target mutations

## Context

The Protocol permits and expects overlap between self-contained Specs. A consumer and provider may
repeat the same wire shape while explaining different local responsibilities. Each target is also a
separate permission boundary: authoring A may replace only A's registered members, and cross-target
work must use separately bound invocations.

The Profile 8 context Service goes further than allowing repeated information. Its maintained Spec
explicitly says that the same physical Markdown file may be registered in more than one target
collection, and the new boundary tests preserve that behavior.

## Expected

Authoring one target changes only that target's Spec revision. Repeated facts may be reconciled
across targets through explicit contract identities and separately authorized target changes, but a
write grant for A does not silently mutate B. A context identity for B changes only after a B-owned
source or explicitly declared shared authority is changed through the appropriate boundary.

## Observed

Registry loading validates uniqueness only inside each target's `documents` array. While iterating
targets, the `paths` map silently overwrites a previous owner when the same path appears again. The
authoring host later accepts any returned replacement whose path is in A's document set; it does not
discover or authorize the other targets that also registered that path.

An executable fixture registered `specs/transfer-promises.md` in both `service.transfer` and
`module.ledger`. `concorde-specify` was invoked only for `service.transfer` and replaced that file.
The Operation succeeded, while a newly resolved `module.ledger` context had a different context ID
even though no Module-bound invocation occurred.

## Impact

Document membership ceases to be a target-local mutation boundary. A single-target author can change
another target's promises, invalidate its active attempts or alter its future agent context. The host
cannot accurately claim that cross-target changes use separate invocations. Review and rollback also
cannot attribute the physical edit to one independent Spec.

The issue is about sharing writable source identity, not about the allowed semantic redundancy
between local consumer and provider descriptions.

## Evidence

- `specs/concorde/services/context-boundary.md:5-10` explicitly permits one Markdown path in several
  collections.
- `src/concorde/specification/repository.py:130-146` overwrites `paths[path]` without rejecting an
  existing owner.
- `src/concorde/capabilities/scoped_operations.py:255-267` authorizes replacement against only the
  selected target's member set.
- `tests/concorde/specification/test_boundaries.py:29-33` asserts shared physical membership but does
  not exercise mutation through one owner.
- Branch-review fixture result: `operation_status=succeeded`, `other_target_changed=true`, and no
  invocation was bound to the other target.

## User Comments

On 2026-09-06 the maintainer rejected global single-owner document semantics and chose collective
shared truth. Every target's resolved context must be self-contained through target-local documents
plus explicitly shared physical Markdown. Sharing is document-granular and one-hop: it does not add
the other referencing entities' remaining Specs. Context provenance must visibly separate Target
Spec from Shared Specs, and project knowledge should avoid unnecessary duplication.

Each physical Markdown declares its exact references and whether it is `main_visible`. Main receives
only main-visible documents through admitted Domain/Service targets and still cannot directly expand
a Module target. A shared document has no unique owner. Ordinary single-target authoring therefore
cannot change it; an accepted topology change must involve every candidate referencing target and
the host may apply the shared replacement only when their separately bounded authors return identical
exact bytes.
