# R-059 · Cross-target Spec reconciliation persists partial semantic changes

## Context

A Domain task may produce work for several participating components. Before any component code is
changed, `Invocation.implement_scope` invokes `concorde-specify` once for each component and then
runs project-wide contract validation. This is intended to reconcile every affected local
consumer/provider view before implementation starts.

Each child `concorde-specify` invocation applies its returned Markdown replacements immediately.
The children share the Domain Operation's isolated worktree, but there is no encompassing proposal
or file transaction for the full set of component Spec changes.

## Expected

A coordinated contract change either establishes a valid set of all affected target views or leaves
the pre-coordination Spec state intact. A gap, invalid contract or failed authoring result from any
participant is reported before the collection is represented as reconciled. No earlier participant
is silently committed as the partial new semantic authority when a later participant blocks.

If partial authoring is intentionally retained for inspection, its lifecycle state, ownership and
resume semantics are explicit and it is not confused with an independently valid target revision.

## Observed

The coordinator loops over components sequentially. Each successful child author call uses
`apply_files` and returns before the next component is assessed. If a later child returns
`spec_incomplete`, `unsupported`, `conflicting` or another blocked outcome, the coordinator returns
that result without rolling back the documents already applied by earlier children. Global contract
validation runs only after every child has succeeded.

An executable two-component fixture made the first component author return a document replacement
and the second return a structured Spec gap. The outer standard loop returned `blocked` with
`spec_incomplete`, but the first component's Markdown replacement remained in the worktree.

## Impact

The worktree can contain a mixture of old and new local contract views after a blocked coordination.
Another Operation may resolve those bytes as current authority even though the intended multi-target
change never reached reconciliation. Retrying can no longer distinguish the originally authored
proposal from the partial state left by the failed attempt. This risk increases as self-contained
Specs intentionally repeat cross-target promises.

## Evidence

- `src/concorde/capabilities/scoped_operations.py:388-398` applies each child author result before
  running global validation.
- `src/concorde/capabilities/scoped_operations.py:392-396` returns immediately when a later child is
  blocked and contains no enclosing rollback.
- `src/concorde/specification/changes.py` provides atomicity for one supplied file set, but the
  coordinator never supplies the combined cross-target set to one transaction.
- Branch-review fixture result: outer `status=blocked`, outcome `spec_incomplete`, and
  `first_edit_persisted=true`.
- `specs/concorde/workflow/how-work-progresses.md:46-50` states that all affected local views agree
  before component implementation, without defining the partial-authoring state.

## User Comments

<!-- Maintainer input when useful or requested. Do not remove this section. -->

Maintainer direction, 2026-09-06: use one linked worktree as the complete candidate change and replace
the separate attempt lifecycle with host-owned `.concorde/worktree.json` state. Partial component
authoring may remain in that candidate when its progress, gap and resume phase are explicit. Run the
cross-component agreement check after all participating authors finish, before implementation.

The primary worktree must retain basic metadata for every live linked worktree in
`.concorde/worktrees.json`. Main cognition must identify ongoing changes in the primary and the
current candidate/status in a secondary. Managed AGENTS.md/CLAUDE.md prompts supplement this declared
context. The primary worktree's branch name is not assumed to be main.

Delivery requires opening an agent in the primary worktree and requesting deliver there. A secondary
session may not change cwd, redirect its runtime or forward delivery as a workaround. The primary
host verifies and merges the complete candidate into its checked-out branch, then removes the
temporary worktree and local state. Local prompt injection is excluded from the merge; primary
delivery receipts distinguish a completed merge from pending cleanup. Component loops stop at ready.
