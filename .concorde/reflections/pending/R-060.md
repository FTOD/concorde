# R-060 · Profile 8 self Specs do not supply their registered Module interfaces

## Context

The new Module kind definition requires the complete registered collection to define provided and
required APIs, including callable signatures, input/output types, preconditions, effects,
obligations, errors, compatibility and representative use. Service Specs must similarly contain the
collaborator promises needed to understand their behavior because child and provider Specs are not
implicitly admitted.

The refactor replaces the former recursive architecture/features with short target-local Specs and
reports successful structural self-validation. This review compared representative maintained
Module and Service documents with their registered API IDs and implementation dependencies.

## Expected

For each registered Module API, the local Markdown collection contains the actual public callable
surface and enough behavioral contract to plan, implement and review a representative change without
opening its parent or a collaborating Spec. For each Service, every collaborator promise required by
its feature is restated locally or represented by a complete local required contract. A structural
validation success is not presented as evidence of semantic completeness.

## Observed

`module.agent-execution` registers `api.execution.execute`. Its document describes
`AgentProcessExecutor` in prose, but the Interface signatures section lists only
`resolve_runtime_bootstrap` and `verify_runtime_bootstrap`; it omits the constructor and callable
execution interface that implement the registered API.

`module.registry` describes `SpecRepository.select`, `documents`, `contracts` and
`implementation_files`, while its signature block lists only four standalone helpers and omits the
class method signatures. `module.spec-publication` registers `api.publication.build`, but its
Interface signatures section contains no signatures at all.

The Operation-host Service implementation imports wire contracts, configuration, permissions,
skill assets, registry, context, file transactions and validation. Its complete three-document
collection declares only one required `contract.context.selection`; it does not locally state the
remaining collaborator API obligations. Those other Module Specs are unavailable to its bounded
planner by design.

The validator checks that an API ID string occurs somewhere in the declared document and that
embedded JSON contract examples conform. It explicitly returns
`semantic_completeness=not_proven`; no representative task assessment is required for self-adoption.

## Impact

Concorde's own Specs can pass every shipped deterministic gate while a compliant bounded agent lacks
the interface information the new Protocol declares mandatory. The missing details may be guessed
from implementation during an implementation stage, but planning and contract decisions cannot use
code and must therefore report Spec incomplete. Model-process doubles that already know the intended
output can make the lifecycle test pass without detecting this gap.

This weakens the branch's claim that Concorde itself demonstrates the adopted Profile 8 model.

## Evidence

- `protocol/kinds/module.md` defines the mandatory complete API view.
- `specs/concorde/modules/agent-execution.md:3-18` omits the callable executor signature for its
  registered API.
- `specs/concorde/modules/registry.md:3-20` omits the described class method signatures.
- `specs/concorde/modules/spec-publication.md:3-11` has an empty signature section.
- `src/concorde/capabilities/scoped_operations.py:20-30` shows the Operation host's immediate local
  collaborators; `specs/concorde/services/operation-boundary.md` declares only the context-selection
  required contract.
- `src/concorde/specification/validation.py` reports structural claims and explicitly does not prove
  semantic completeness.
- `tests/concorde/specification/support.py#ModelProcessDouble` supplies predetermined plans/tasks and
  implementation behavior rather than assessing the missing self Specs.
