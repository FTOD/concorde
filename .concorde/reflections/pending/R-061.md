# R-061 · Standalone code review has no public capability entry

## Context

Protocol 4.0.0 and Profile 11 provide a dedicated code-review phase with scoped implementation
reads, a fresh reviewer, no write grant and typed findings. The development loop uses this internal
stage. Reflection investigation separately runs a read-only implementation worker for selected
Reflection records.

Users also request ordinary branch review, diagnosis or source inspection without a Reflection
record or a development task. This reflection concerns the public entry for those standalone tasks.

## Expected

A standalone observational source task has a public capability path that selects its owning Module,
grants scoped implementation reads without writes and returns declared findings. It does not need
to enter a development lifecycle or select an unrelated Reflection to obtain that behavior.

This is a requested workflow capability, not a claim that P7 prohibits developer-authorized outer
maintenance: P7 explicitly permits such a session to inspect the project directly.

## Observed

`concorde-review` is an internal stage, excluded from `SKILL_NAMES`. Both the public launcher and
Studio reject it as a direct entry. `concorde-main` exposes ask and topology actions; its coordinator
uses Spec discovery context and does not grant implementation reads for a source-review request.

The development loop reaches code review through its change workflow. Reflection investigation
requires explicitly selected records. Neither is a standalone observational review entry.

The internal review helper already supports a checkout without a managed change, using HEAD as its
baseline. Its trusted, already-routed in-process invocation is not exposed as a public developer
workflow. The missing piece is therefore public access and routing, not the review mechanism itself.

## Impact

Users cannot request a standalone branch review or source diagnosis through the shipped public
capabilities with the existing bounded review guarantees. They can perform explicitly authorized
outer maintenance, but that does not supply the missing public workflow. The same gap affects
investigation of a failed check when no Reflection or development task has been selected.

## Evidence

- Revalidated on 2026-09-10 at `5277d68238335869005204714d4db2145820bfea`.
- `src/concorde/spec/contracts.py` defines `REVIEW_STAGES`, `STAGE_CAPABILITIES` and `SKILL_NAMES`;
  `capabilities/review.py` declares review as an internal stage.
- `scripts/run-capability.py` and `src/concorde/harness/studio.py#build_studio_graph` admit public
  Skill names only. Running `.venv/bin/python scripts/run-capability.py concorde-review` returned
  exit 3, `status: blocked`, `unknown_capability` and `workspace: null`, without entering a workflow.
- `capabilities/main.py` exposes ask/topology; `src/concorde/development/capability_host.py`
  supplies the coordinator with discovery context. `capabilities/dev_loop.py` composes code review
  into development.
- `src/concorde/development/review.py` binds `write_roles=()` and rejects write grants;
  `specs/concorde/development/interfaces.md` documents its internal entry and unmanaged HEAD baseline.
- `src/concorde/reflections/scoped_triage.py` requires selected records for investigation.
- Three focused tests passed: `ReviewTests.test_modes_use_full_collection_fresh_sessions_and_no_write_grants`
  in `tests/concorde/development/test_review.py`,
  `RunCapabilityLauncherTests.test_refuses_a_stage_capability_name` in
  `tests/concorde/development/test_run_capability.py`, and
  `StudioTests.test_internal_stages_cannot_be_published_as_direct_studio_entries` in
  `tests/concorde/harness/test_studio.py`.
- `generated/protocol/principles.md` P5/P7 distinguishes code-review authority and explicitly
  permits developer-authorized outer maintenance.

Developer-selected resolution, implemented in the current checkout on 2026-09-10:

- Expose `concorde-review` as a public global capability and Skill, with `spec` and `code` modes.
- Route new observational tasks through the Spec-only coordinator, then invoke the existing
  fresh, read-only reviewer. Existing bound development calls reuse their selected target.
- Admit the Skill through the public launcher and Studio, and distribute its Codex and Claude
  projections. Keep the current-worktree scope, typed findings and existing baseline semantics.
- Independent review requires neither a managed change nor a selected Reflection record.

Validation: the full Python suite ran 612 tests with 0 failures, 0 errors and 8 optional Studio
server tests skipped (604 passed). `build --check` passed; Spec validation reported 0 errors and
37 existing coverage warnings. New standalone-review tests cover both modes, routing without a
target hint, scoped read-only grants, HEAD baseline, unchanged project files, report persistence,
blocked routing, and policy preview. Launcher, build, installation and development-loop regression
tests passed. These are local implementation results; this record has not been closed or delivered.
