# R-063 · Public capability launchers accept outer enforcement without supplying sandbox attestation

## Context

`concorde-capability-configuration@1` accepts `native` and `outer` enforcement for both
Codex and Claude. Initialization and configuration changes persist either value. Outer enforcement
requires trusted host evidence identifying the active sandbox; task JSON cannot supply that
authority.

The installed public Skill launcher delegates to `json_main`. Local execution constructs a
`CapabilityHost`; when `CONCORDE_STUDIO_URL` is set, execution is delegated to the Studio
adapter, which constructs its own host.

## Expected

A supported project configuration has an executable public path. For outer enforcement, a trusted
launcher supplies evidence of the active sandbox and binds it to the invocation. If the distributed
launchers cannot supply that evidence, initialization or configuration rejects outer enforcement
rather than accepting settings that fail when an Agent stage renders its policy.

## Observed

The configuration schema accepts `enforcement: outer`, and project initialization persists it
without checking launcher support.

The local `json_main` path constructs
`CapabilityHost(Path.cwd(), package_root, mode=value["mode"])`, leaving `outer_sandbox` at its
default `None`. The Studio adapter also constructs its execution host without `outer_sandbox`;
its public graph-construction interface exposes no sandbox-attestation argument.

Agent stages pass the stored enforcement selection and `host.outer_sandbox` to the integration
renderer. Both renderers reject outer enforcement without sandbox evidence.

A maintenance recheck initialized temporary projects with outer enforcement for both integrations
and verified that their stored configurations loaded successfully. An injected `json_main`
runner then confirmed `host.outer_sandbox is None` and exercised the corresponding renderer.
Codex and Claude both rejected the missing evidence. This probe did not execute a capability graph
or launch a model.

## Impact

An initialized project can accept settings that prevent Agent stages from launching through the
distributed local and Studio boundaries. Deterministic capabilities and actions are not necessarily
affected. Trusted embedders can construct a `CapabilityHost(outer_sandbox=...)`, but the
distributed launchers do not provide that attestation path.

## Evidence

- Revalidated on 2026-09-10 at `5277d68238335869005204714d4db2145820bfea`.
- `src/concorde/spec/typed_data.py` admits both enforcement values.
  `src/concorde/spec/initialize.py` validates and persists the supplied configuration.
  `src/concorde/development/configuration.py` validates configuration proposals and applications
  against the same schema without checking launcher support.
- `scripts/run-capability.py` delegates the public launcher to
  `src/concorde/development/capability_host.py#json_main`, which selects Studio or constructs the
  local host without evidence. `CapabilityHost` defaults `outer_sandbox` to `None`.
- `src/concorde/harness/studio.py#build_studio_graph` constructs the Studio execution host without
  sandbox evidence.
- `src/concorde/development/capability_host.py` passes the enforcement selection and host evidence
  to the renderer. `src/concorde/harness/permissions.py#render_codex_configuration` and
  `#render_claude_configuration` reject missing evidence.
- `specs/concorde/development/interfaces.md` and `specs/concorde/spec/initialize.md` advertise
  outer enforcement. `specs/concorde/harness/runtime-values.md` requires verified host evidence
  and excludes task JSON as its source.
- Temporary consumer probes for Codex and Claude both initialized and loaded outer configuration
  successfully. The public-host/renderer boundary then rejected it with the respective
  `no outer enforcement was verified` error. These probes exercised configuration and policy
  rendering, not end-to-end Agent execution.
- `PermissionTests.test_unavailable_native_enforcement_requires_verified_outer_boundary` in
  `tests/concorde/harness/test_permissions.py` passed; it verifies rejection without evidence
  and acceptance with a supplied trusted-host identity.
