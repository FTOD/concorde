# R-072 · Blocking-finding to gap pairing relies on verbatim string equality

## Context

A Spec review inside `concorde-dev-loop` (change `change.c268520b-af25-48bc-a91f-d806977a1744`,
root target `module.concorde`) returned two blocking findings, each with a semantically matching
gap, and the host rejected the whole completion with
`invalid_completion: blocking Spec finding requires its concrete gap`. The loop ended `failed`
with coverage `module.concorde/spec=incomplete`; the reviewer's gaps were discarded and never
reached the human decision point that `spec_incomplete` is designed to provide.

The Development contract (`specs/concorde/development/interfaces.md`, "A blocking Spec finding
requires a gap with blocked_step=affected_task and needed_contract=contract") and its realization
(`src/concorde/development/review.py#_validate`) pair a blocking finding with its gap by byte
equality of two free-text fields: `gap.blocked_step == finding.affected_task` and
`gap.needed_contract == finding.contract`. The `concorde-review-stage-result@1` gap shape carries no
reference to a finding, so those two strings are the only join key.

The immediate cause was an instruction gap: the spec-review mode and the shared review-scope prompt
asked for "a question/blocked_step/needed_contract gap" without saying the two fields must be
verbatim copies. Commit `569ac7ba` (`fix(agents): state the blocking-finding gap equality rule for
reviewers`) closed that gap by stating the rule in both instruction sources. This record keeps the
remaining design question, which the instruction fix does not remove.

## Expected

A reviewer that reports a blocking Spec finding together with a concrete, attributed gap should
produce an admissible result. The pairing between a finding and its gap should be an explicit,
stable identity that a model can satisfy reliably, not a coincidence of wording. When pairing fails,
the human should still see the reviewer's findings and gaps rather than only "review could not
complete".

## Observed

The reviewer returned, for `finding.concorde.boundary-interfaces`, `affected_task` "Invoke Framework
capabilities through Skills, lifecycle commands and Studio while preserving the declared authority
boundary." and `contract` "Ontology / Entities; Developer entry points", and a gap whose
`blocked_step` was "Establish the architecture contract for capability invocation and Studio
execution at the root boundary." and whose `needed_contract` was "Interface entities with stable
identities, responsibilities and labeled relationships to the children providing invocation and
Studio execution." The second pair had the same shape. Every gap was attributable to its finding by
meaning; none matched by bytes, so `_validate` raised `invalid_completion` and the host recorded the
review as `incomplete`.

The reviewer's own completion gate reported "each blocking finding has an attributed gap", showing
it believed the contract was met. The unit tests in `tests/concorde/development/test_review.py`
construct both sides of the pair from one helper (`gap()` supplies the finding's `contract` and
`affected_task` and the gap's fields), so they exercise the host rule but cannot reveal that a real
reviewer has no way to know it.

With the instruction fix, admission depends on the model copying two strings exactly. Any wording
drift, whitespace change or model that paraphrases still fails the entire review, and the failure
mode remains opaque: an `incomplete` review with an `invalid_completion` error, not a
`spec_incomplete` stop with visible gaps.

## Impact

Until the instruction fix, every Spec review that found a blocking problem failed; only
`no_findings` or advisory-only reviews could pass, which silently disabled the loop's main Spec
quality gate. After the fix, the gate works but rests on verbatim copying by a model. A failure
discards the reviewer's work and surfaces as a generic failure, so the human loses exactly the
information a blocking review exists to deliver.

## Evidence

- [Rejected review completion and host failure](../evidence/R-072-review-rejection.json): the
  reviewer's full `concorde-review-stage-result` (findings, gaps, gates) and the host's
  `invalid_completion` record from invocation `22445c00-9c23-49d2-9195-6b79f587cbf0`.
- `src/concorde/development/review.py#_validate`: the equality check on `blocked_step` and
  `needed_contract` for blocking findings in spec mode.
- `specs/concorde/development/interfaces.md`, "The reviewer returns concorde-review-stage-result@1"
  paragraph: the contract sentence the check implements.
- `src/concorde/spec/contract_shapes.py` `GAP` and `src/concorde/spec/contracts.py`
  `concorde-review-stage-result`: neither shape carries a finding reference or field descriptions.
- `agents/spec_engineer/modes/spec-review.md` and `prompts/workflow-host/review-scope-and-result.md`
  at `569ac7ba`: the instruction sources now stating the verbatim-copy rule.
- `tests/concorde/development/test_review.py` `gap()` helper: both sides of the pair built from one
  value.

Candidate directions, recorded for triage rather than decided here:

- Let a review gap reference its finding by `id` (an optional `finding_id` on gaps that originate
  from a review), and pair by that reference instead of by text.
- Let the host derive `blocked_step` and `needed_contract` from the finding's `affected_task` and
  `contract`, so a blocking finding carries only its `question`; the reviewer never restates the
  two fields.
- If the equality rule is kept, give the wire schema field descriptions that state it, so the rule is
  visible to any consumer of the schema and not only to the two instruction files.

Each direction changes `interfaces.md`, the gap or finding wire shape, `review.py`, the reviewer
instructions and the review tests together; the change belongs to `module.development` with the
shared wire shapes listed by `module.spec` and `module.harness` reviewed separately.
