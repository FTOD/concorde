# R-049 · Coarse directory locators in one capability module deny sibling planners their own files

## Context

While re-partitioning `specs/concorde` into capability modules (understanding, lifecycle,
reflections, capabilities, distribution, auto-docs) for `feature.concorde.define-project-ontology`,
several features now require an interface that another capability module provides: for example
`feature.understanding.explore-alignment` requires `contract.capabilities.tools`,
`feature.lifecycle.standard-development-loop` requires `contract.capabilities.agent-surface`, and
`feature.distribution.package-concorde` requires `contract.capabilities.agent-surface`. The
`capabilities` module truthfully owns directory-typed entities whose locators are whole directories:
`skills`, `operations`, `.agents/skills`, `.claude/skills`. Every module also owns a `tests` entity
whose locator is `tests/concorde`.

## Expected

Per `contract.understanding.planning-context` and FR-009/FR-010 of the former
permission-bounded-planning feature, the plan author for a selected feature reads its own module's
owned locators (for `understanding`, that includes `skills/concorde-context/SKILL.md` and
`scripts/workspace.py`) while the required provider module's private internals are denied.

## Observed

`_provider_private_paths` in `src/concorde/understanding/planning_context.py` denies every entity locator of a
foreign provider module except the included provider feature files. When the provider is
`capabilities`, the deny set contains the directories `skills` and `operations` and the file
`tests/concorde`, while the selected module's owned set contains files below those directories
(`skills/concorde-context/SKILL.md`) or the identical `tests/concorde` path. Exact-path filtering
removes only identical strings, so the compiled policy carries both `read skills/concorde-context/SKILL.md`
and `deny skills`. `src/concorde/capabilities/operation_permissions.py` renders both without checking nesting;
under Claude permission rules a deny wins over an allow, so the planner cannot read its own Skill
prompt or tests, and under Codex the precedence depends on the host. The same shape existed before the
re-partition (`entity.skills.sources` → `skills`, `entity.runtime.tests` → `tests/concorde`) but
cross-module requirements were rarer.

## Impact

Planning still resolves without an error, so the attempt proceeded. The bounded assumption taken was
to keep directory-typed entities truthful, remove the artifact-type `scripts` directory entity from
`capabilities`, narrow the projected surface locators to `.agents/skills` and `.claude/skills`, and
plan to give each module's `tests` entity a capability-specific directory once `tests/concorde` is
split by capability. Cross-module planning launches that require a `capabilities` interface remain
over-restricted until the nesting rule between owned files and provider directory denies is decided.

## Evidence

- `src/concorde/understanding/planning_context.py#_provider_private_paths` (exact-string `included`/`denied`
  filtering) and `resolve_planning_context` (`owned = raw_owned - private_set`).
- `src/concorde/capabilities/operation_permissions.py` (`_normalized_policy`, Claude `permissions.deny`
  rendering) never compares nested allow/deny paths.
- `specs/concorde/modules/capabilities/architecture.md` entities `entity.capabilities.skill-sources`
  (`skills`), `entity.capabilities.operation-sources` (`operations`), `entity.capabilities.tests`
  (`tests/concorde`).
- Reproduction: `python3 -c "from concorde.planning_context import resolve_planning_context as r; c=r('.', 'specs/concorde/modules/understanding/features/006-explore-alignment.md'); print([p for p in c.denied_paths if p in ('skills','operations','tests/concorde')]); print([p for p in c.owned_implementation_paths if p.startswith('skills/')])"`
  run with `PYTHONPATH=src` from the repository root.

## Triage Analysis

Verified at commit `c65fab108fc2d241249b2e0015cb023843dde3fd` on 2026-09-04. The
recorded reproduction has changed: `concorde.planning_context` moved to
`concorde.understanding.planning_context`, and the former shared `tests/concorde` collision
disappeared after tests were partitioned by capability.

The remaining problem is current and reproducible. Describing the real `concorde-plan` policy for
`feature.understanding.explore-alignment` produces readable paths such as
`skills/concorde-context/SKILL.md` together with the denied ancestor `skills`. Equivalent conflicts
exist between owned `operations/*` and denied `operations` for Lifecycle and Distribution features.

The root cause is that `module.concorde.capabilities` truthfully owns physical container locators
`skills` and `operations`, while other modules own individual artifacts beneath those directories.
`_provider_private_paths` converts all foreign-provider locators into denies, but context resolution
removes and rejects only exact-string intersections. The policy compiler therefore carries both
ancestor and descendant paths into native rules. Existing tests cover exact collisions only.

The owning planning-context contract also defines only exact-path precedence. Resolving the defect
requires first specifying integration-neutral ancestor/descendant semantics, so the route is
`specify`, not `fast-loop`.

## Proposed Resolution

Route R-049 to `specify` under `feature.understanding.bound-planning-context`. Preserve the existing
exact-collision rule. When a foreign provider deny is an ancestor of an exact selected-owned child,
omit only that ancestor deny; default-deny continues to exclude unlisted siblings. When a broad
selected-owned locator contains a provider-private descendant, fail closed. Require successful
read/write and deny sets to be hierarchically disjoint, then add unit and end-to-end policy evidence
for the current `skills` and `operations` layout.

## Intervention Rationale

Human intervention is not required to determine the route. Existing authorities already require
selected-module owned locators to remain readable, separate physical distribution layout from
artifact ownership, and keep every unlisted path default-denied. Those constraints determine the
directional containment rule without a product or external-state choice. Because implementation
would change a normative Concorde permission contract, it must still use the explicitly authorized
`feature.concorde.evolve-protocol` cutover rather than an ordinary reflection implementation.
