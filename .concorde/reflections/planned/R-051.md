# R-051 · Codex 0.153 rejects generated named permission profiles

## Context

While investigating pending reflections R-049 and R-050 through the paired
`concorde-reflections-triage` Operation in an isolated worktree, both zero-write investigator
launches used the Codex native configuration compiled by
`src/concorde/capabilities/operation_permissions.py`.

## Expected

Per `feature.capabilities.permission-bounded-execution`, a supported Codex client accepts the
generated named permission profile, enforces its exact read/deny/network boundary, and starts the
investigator; incompatible native syntax fails only when no supported native or approved outer
boundary can represent the normalized policy.

## Observed

With `codex-cli 0.153.2`, both launches stopped before the model ran. The generated command supplied
`default_permissions="concorde-..."` plus nested `permissions.<profile>.*` configuration, and Codex
returned `Error loading config.toml: invalid type: map, expected a boolean in permissions`. The
executor's version preflight accepted 0.153.2 because it only enforces the existing minimum version.

## Impact

The paired Operation produced no investigator result for either pending reflection, so every
downstream persistence step was stopped. The bounded continuation used the dedicated read-only
`reflection_investigator` role and kept the parent as the only triage writer; no permissive native
retry or unverifiable outer-sandbox claim was used.

## Evidence

- `codex --version` reports `codex-cli 0.153.2`.
- Reproduction for both IDs:
  `python3 scripts/run-operation.py operations/concorde-reflections-triage/operation.py 'investigate R-NNN' --framework-prefix . --feature-path <direct-feature> --execute`.
- Both traces end in `src/concorde/capabilities/operation_executor.py#AgentProcessExecutor.__call__`
  with Codex exit 1 and the same `invalid type: map, expected a boolean in permissions` diagnostic.
- `src/concorde/capabilities/operation_permissions.py#render_codex_configuration` emits the named
  `permissions.<profile>` map and `default_permissions` selector.
- `specs/concorde/modules/capabilities/features/003-enforce-permission-bounded-execution.md` defines
  native-syntax evolution and fail-closed compatibility obligations.

## Triage Analysis

Verification outcome: `reproduced` on 2026-09-04 at commit
`1c8d9e2b8e0d88d3a1567243628da315e0e24bc1`.

The exact isolated `concorde-reflections-triage ... investigate R-051 --execute` launch still exits
1 before its investigator starts with `invalid type: map, expected a boolean in permissions` on
`codex-cli 0.153.2`.

The immediate defect is argv serialization, not rejection of named permission profiles. The
renderer first constructs one nested profile, then flattens dynamic keys such as `.`,
`.concorde/reflections`, and paths ending in `.md` into separate dotted `-c` override names. Codex's
override parser treats dots inside those quoted dynamic segments as additional hierarchy, producing
a map where the profile schema requires a Boolean or access value. The same generated profile passed
as one TOML inline-table override loads successfully with `psp` disabled, and an ephemeral no-tool
Codex invocation completed successfully.

This excludes ambient configuration and the client version floor: the argv ignores user config, the
committed checkout contains no project `config.toml`, Codex 0.153.2 accepts the inline form, and the
official profile compatibility floor remains 0.138. The generated profile also needs schema
normalization: `:root`, `:minimal`, `:tmpdir`, and `:slash_tmp` are direct filesystem keys, while
project-relative rules belong below `:workspace_roots`; the renderer's internal
`features.network_proxy` value must not be omitted from argv.

Existing tests miss the defect because the installed-client test appends `--help`, which exits before
loading the generated configuration. The maintained permission-bounded-execution contract already
requires parser-valid named profiles, exact effective boundaries, deterministic native rendering,
and fail-closed execution, so correcting this serializer restores specified behavior and qualifies
for `fast-loop`; it does not change Protocol semantics.

A schema-correct profile exposes a distinct npm-local runtime mounting failure on the first sandboxed
tool call. That problem is recorded separately as R-052 and is not part of R-051's serializer fix;
R-051 implementation must not claim that the complete Operation is restored while R-052 remains
open.

## Proposed Resolution

Route R-051 to `fast-loop` under `feature.capabilities.permission-bounded-execution`. Serialize the
complete digest-named Codex profile as one deterministic TOML inline-table value under a static
`permissions.<profile>` override, keep dynamic paths out of dotted override names, normalize special
and workspace-relative filesystem rules to the documented shape, and emit the complete configured
feature/network posture. Replace the `--help` false positive with a no-model probe that actually
loads the generated config. Preserve the normalized policy, version floor, strict config,
non-interactive approval, ignored user config, and fail-closed behavior. Keep R-052 outside this
change.

## Intervention Rationale

Human intervention is not required. Existing project contracts, the reproduced diagnostic, official
Codex profile schema, and successful inline-profile probes determine one bounded conformance fix.
No product preference, credential, user/project configuration migration, permissive retry, outer
sandbox claim, or normative Protocol decision is needed.
