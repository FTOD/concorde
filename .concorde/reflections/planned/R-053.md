# R-053 · Agent process exit zero masks a capability that could not start

## Context

After implementing R-051's parser-safe Codex permission profile, the real
`concorde-reflections-triage` Operation was run against R-052. The profile loaded and the nested
Codex agent started, but every required read-only tool failed because its sandbox could not execute
the npm-local Codex vendor binary.

## Expected

Per `feature.capabilities.permission-bounded-execution`, an investigator that cannot run its
mandatory workspace gate or inspect any authorized source is a failed capability. Its enforcement
receipt reports failure, and the Operation stops every downstream node rather than accepting prose
that describes the failure as a successful capability result.

## Observed

The nested agent truthfully returned that investigation could not start, named the failed
`scripts/workspace.py --phase analyze` prerequisite, reported the bubblewrap `execvp` error, and
stated that no project files were inspected. Codex nevertheless exited 0. `AgentProcessExecutor`
derives success only from that process exit code, so the Operation emitted a receipt with
`status: success`, `exit_code: 0`, and `limitations: none` and returned the failure prose as an
ordinary successful `concorde-analyze` result.

## Impact

The investigate action happened to have no later model stage, but the same false-success boundary
can allow a multi-stage Operation to continue with an unusable prior result after a mandatory Skill
could not execute. Exit-code-only success does not establish that a capability completed its
contract, and the current receipt loses the limitation the agent explicitly reported.

## Evidence

- Reproduction:
  `python3 scripts/run-operation.py operations/concorde-reflections-triage/operation.py 'investigate R-052' --framework-prefix . --feature-path specs/concorde/modules/capabilities/features/003-enforce-permission-bounded-execution.md --execute`.
- Result output begins `Investigation of R-052 could not start because the execution environment
  failed before the mandatory workspace gate` and says no project files were inspected or changed.
- The adjacent receipt reports `status: success`, `exit_code: 0`, and `limitations: none`.
- `src/concorde/capabilities/operation_executor.py#AgentProcessExecutor.__call__` maps return code 0
  directly to success without a capability-result schema or semantic completion signal.
- `specs/concorde/modules/capabilities/features/003-enforce-permission-bounded-execution.md` requires
  executor refusal and capability failure to stop all downstream nodes.

## Triage Analysis

Verification outcome: `reproduced` on 2026-09-04 at commit
`84fcd1916d4e7542c06b9ce0bb1591565f825505`.

The real R-052 investigation exits 0 even though its only capability output says the mandatory
workspace gate could not run, every command failed before execution, and no source was inspected.
The adjacent receipt nevertheless reports `status: success`, `exit_code: 0`, and
`limitations: none`.

`AgentProcessExecutor` derives status and limitations solely from child return code, raises only on
nonzero, and treats arbitrary stdout from a zero-exit process as successful. The execution result has
only an output string and receipt; the Operation runtime validates only those types before appending
the value as a successful `CapabilityResult`. There is no typed semantic completion signal.

Existing leaf, standard-loop, and permission-execution contracts already require mandatory gate,
workspace, tool, invalid-result, and executor failures to stop the Skill and every downstream node.
The missing part is an integration-neutral representation of semantic capability completion.
Process exit 0 is necessary transport evidence but is insufficient phase-completion evidence.

Codex exposes JSONL lifecycle events and schema-constrained final output; Claude exposes analogous
JSON/schema facilities. Phrase matching is unsafe, and treating every failed tool as fatal is also
wrong because a capability may diagnose and recover. The specification must define a typed outcome,
required completion evidence, identity binding, and host validation rules before implementation.

This is not fast-loop eligible because it changes the Skill/Operation result interface, native
client contract, receipt semantics, and downstream state rules. Route R-053 to `specify`; eventual
implementation changes normative Concorde Protocol semantics and requires an explicitly authorized
`feature.concorde.evolve-protocol` cutover. R-052 remains out of scope.

## Proposed Resolution

Route R-053 to `specify` under `feature.capabilities.permission-bounded-execution`. Define one
versioned integration-neutral capability-completion envelope with semantic success/failure, usable
output, limitations, required gate evidence, and launch/policy/configuration identity. Require zero
exit to be insufficient, malformed/missing/stale/failed completion to raise before state admission,
and only validated success to become `CapabilityResult`. Use native Codex/Claude structured-output
facilities without prose matching or blanket tool-failure heuristics, then reconcile through
`feature.concorde.evolve-protocol`.

## Intervention Rationale

Human intervention is not required to determine the behavior or route. Existing contracts already
say this capability failed and downstream execution must stop; current client facilities and source
establish the need for a typed completion contract. The later Protocol cutover still requires
explicit maintainer authorization as a process boundary, not as an unresolved product decision.
