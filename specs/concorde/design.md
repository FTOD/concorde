# Design Reference: Concorde

This reference explains and justifies the root level of Concorde's specification hierarchy. It never
redefines responsibility, boundary, organization, or contracts; those remain owned by `module.md`,
`architecture.json`, and the contract documents.

## Implementation Notes

### Maintained sources and installed mirrors

- `presets/concorde-core/` holds the composition layer: four templates (three append-composed
  spec/plan/tasks guidance layers and one replacement template for the feature root's accepted
  realization) plus complete replacement layers for the nine path-sensitive normal Spec Kit
  commands.
- `extensions/concorde/` holds the active capability package: five command definitions
  (`speckit.concorde.init`, `speckit.concorde.context`, `speckit.concorde.validate`,
  `speckit.concorde.feature.harden`, and the agent-only `speckit.concorde.ask`), the portable
  launchers `extensions/concorde/scripts/bash/concorde.sh`,
  `extensions/concorde/scripts/powershell/concorde.ps1`, and
  `extensions/concorde/scripts/python/concorde.py`, the selected-workspace adapter
  `extensions/concorde/scripts/python/workspace.py`, and the standard-library Python (3.11 or
  later) runtime under `extensions/concorde/runtime/concorde/`.
- `bundles/concorde-bundle/` holds the recipe that pins the tested preset and extension pair;
  `catalogs/` advertises the three release units with location, compatibility, digest, and trust
  metadata.
- `.specify/presets`, `.specify/extensions`, the three composed core templates under
  `.specify/templates` (`spec`, `plan`, `tasks`), `.agents/skills`, and `.claude/skills` are verified
  installed mirrors regenerated by `scripts/development/self-host-concorde.py propose|apply` and by
  Spec Kit's own `preset add --dev` / `extension add --dev --force`; they never flow back into
  sources. The tracked `.specify/scripts/bash/*.sh` helpers (which emit `FEATURE_IMPLEMENTATION`) and
  the `design.md`-to-`implementation.md` tree line in the composed plan template are Concorde-owned
  local edits, not Spec Kit outputs.
- `docsite/` is the TypeScript Docusaurus project that publishes the read model; `generated/` and
  `docsite/.generated/` are ignored delivery and projection trees.
- `specs/concorde/` is this hierarchy: the root module, four child modules, and twenty feature
  roots; `.concorde/config.json` records the Architecture Source Profile in force.

### Launcher and runtime model

The four runtime-backed operations reach the runtime through project-relative launchers regardless
of the skill or slash-command syntax that displays them; results are versioned canonical JSON
envelopes produced by `diagnostics.py`. `ask` has no runtime verb: the coding agent follows the
installed procedure directly and answers read-only from cited installed guidance and the smallest
relevant maintained sources. The nine preset command overrides call `workspace.py --phase` as the
sole path authority before any artifact is read or written, so selected-workspace routing precedes
every inherited root-path assumption. Inside the runtime, `repository.py` owns canonical discovery
and safe path classification, `feature_workspace.py` and `cli.py` own workspace resolution and phase
paths, `initialize.py`, `context.py`, `readiness.py`, and `validate.py` own the deterministic
operations, `validation/` holds the rule families (hierarchy, layout, summary, contracts, scenarios,
evidence, freshness), and `feature_hardening.py` owns approval-gated, atomic hardening.

### Spec Kit ecosystem placement

Spec Kit resolves trust and compatibility, previews the expanded plan, installs components, records
provenance, and materializes commands through the target project's active coding-agent integration.
The `concorde-bundle` bundle is a non-executable recipe: it names and pins the independently
versioned `concorde-core` preset and `concorde` extension that were tested together and contains no
workflow steps of its own. The preset's template layers add Concorde prompts and gates to Spec Kit's
existing templates and its command layers override the nine affected lifecycle surfaces; phase
meanings are unchanged. The extension's four operational surfaces invoke the same deterministic
Architecture Core runtime; the fifth, `ask`, is agent-followed and read-only. Release archives are
built from explicit allowlists with stable member ordering, permissions, timestamps, versions, URLs,
and SHA-256 digests; the base URL embedded in catalog metadata describes where the catalog and
archives will be served and is never contacted during a build. A release is accepted only from built
artifacts installed into checkout-isolated projects.

### Self-hosting

The repository bootstrap `scripts/development/self-host-concorde.py` lives outside the installed
extension so a checkout with no active installation can still inspect and install the framework.
`propose` validates the source boundary and active integration, computes a deterministic source
digest, and writes only an ignored proposal; `apply` accepts only that proposal, preflights the same
components in an isolated Spec Kit project, materializes through Spec Kit's public development-mode
lifecycle, and atomically writes an ignored receipt; `status` performs no writes and
`status --require-current` is a non-mutating quality gate. The bundle recipe constrains this
composition but is not executed as a self-hosting runtime.

### Host integration records and mirror regeneration

Spec Kit 0.16.4 materializes only its five core template names (`checklist`, `constitution`,
`plan`, `spec`, `tasks`) into `.specify/templates/`; a preset `replace` template with a new name,
such as `implementation-template`, is reached solely through `specify preset resolve` and has no
composed mirror. Spec Kit registers preset and extension commands for one active integration at a
time and reads that choice from both `.specify/integration.json` and `.specify/init-options.json`
(including the `skills` option); a refresh under the `claude` integration therefore rewrites the
`claude` skills and unregisters the `codex` ones, and vice versa. Because the self-hosting tooling
recognizes only `codex`, regenerating every mirror means temporarily setting both records to codex
in skills mode, running `propose` → `apply` → `status --require-current`, backing up the fourteen
codex skills, restoring the `claude` records, re-materializing the `claude` skills through Spec
Kit, and restoring the codex skills. `extension add --dev` also writes a `.specify-dev/` cache of
per-integration rendered commands inside the installed extension; the self-host digest ignores that
subtree and it is git-ignored. Docusaurus keeps a persistent bundler cache under
`docsite/node_modules/.cache`; run `docusaurus clear` after editing the content plugin, or stale
compiled pages are served. A summary's declared view link is rewritten by the content plugin to the
delivered view route with the `pathname://` protocol so the router's route-only broken-link check
accepts the static file.

## Design Rationale

### Why a summary that is read and a reference that is consulted

The constitution requires every level to be understandable from one summary in minutes, yet the
whole specification must stay complete. Splitting `module.md` (responsibility, boundary, level view,
inventories, one representative scenario, key rationale) from `design.md` (implementation details,
ideas, alternatives, decisions) gives humans and coding agents one bounded interface per level while
keeping narrative available on demand. The summary is held to a 4,000-word reading budget (about 20
minutes) and to a fixed section shape so the check is deterministic; the reference is unbounded,
navigable by stable headings, reachable from the summary, and never an implicit input to any
workflow operation. `design.md` is reserved for modules and `implementation.md` for feature roots so
the two kinds of reference cannot be confused and no compatibility alias is needed.

### Why Spec Kit is the host

Concorde must not become a second orchestrator. Spec Kit already owns specification, clarification,
planning, tasks, implementation, analysis, convergence, and issue conversion, plus component
resolution and provenance. Composing a preset into the existing commands and registering an
extension through the active coding-agent integration reuses that lifecycle, keeps feature creation
and selection as standard Spec Kit behavior, and lets a maintainer install, verify, update, and
remove Concorde with the tools they already use.

### Why deterministic validation and approval-gated hardening

Maintained sources are the only authorities, so their integrity has to be checkable without
judgment: validation is read-only, reports every independently detectable finding in deterministic
order with a stable rule ID and remediation, and repeated runs are byte-equivalent. Durable
documents change only through reviewed proposals bound to a source digest and applied atomically,
which keeps an implementation attempt from silently rewriting accepted realization or module
rationale. Generated views, sites, catalogs, receipts, and manifests are reproducible evidence, not
intent.

### Why hardening may amend the module reference

Ideas, alternatives, and implementation detail are produced while an attempt is in progress, but
the attempt's files are removed when it is hardened. Letting the same reviewed, digest-bound
proposal carry that material into the providing module's `design.md` keeps it durable without
opening a second write path: nothing else in the workflow writes a module reference, the proposal
replaces the whole file so review sees exactly what will exist, the source digest covers the current
reference so a concurrent manual edit is a conflict, and maintainers keep the ordinary right to edit
the reference directly.

### Why the root view stops at one level

Each level shows only its immediate modules, current-level features, boundary contracts, and
permitted external actors. Deeper detail is reached by zooming, so a reader is never asked to hold
more than one level at a time and feature-owned explanatory views can illustrate collaboration
without expanding the canonical structure.

## Alternatives Considered

- Concorde-owned feature creation and selection commands (`feature.create`, `feature.select`) were
  removed on 2026-08-27 in favour of the standard Spec Kit selection (`.specify/feature.json`
  written by specify or `SPECIFY_FEATURE_DIRECTORY`); a second store or lifecycle contradicted
  Spec Kit's ownership.
- A Concorde `subfeature.create` namespace or batch decomposition proposal step was rejected:
  sub-features are created by the normal specify phase, and invalid depth, duplicate identity,
  module disagreement, and unsafe paths are rejected by deterministic validation and workspace
  resolution rather than by a proposal.
- A throw-away migration command or script for the document-model refactor was rejected; renaming
  the feature-level references with `git mv`, authoring the five module references, and rewriting
  the five summaries is bounded, reviewable, and named by validation when incomplete.
- Compatibility aliases or symlinks for renamed documents and a transition window for the renamed
  protocol fields were rejected because Concorde is the only adopter and clean breaks keep every
  consumer on one name.
- Free-form summary headings detected heuristically were rejected in favour of eight fixed H2
  sections so the shape check is deterministic.
- Diff or patch semantics for hardening proposals were rejected in favour of full-content
  replacement so apply stays byte-exact, reviewable, and digest-bound; two sequential single-file
  applies were rejected because a failure between them leaves the non-atomic state the workflow
  forbids.
- Front matter and a registrable ID on the module reference were rejected to avoid a second
  authority for module facts; optional presence was rejected because every module must own one.
- A preset template for the module reference was rejected; the runtime already seeds `module.md`
  and `design.md` at initialization, and a preset entry would split that authority.
- Keeping the documentation collection identifiers while only changing file globs was rejected
  because manifest consumers would see pages whose provenance no longer matched their source name.
- Extending the self-hosting tooling to the `claude` integration inside the document-model attempt
  was rejected as feature 004 scope; the two-record integration switch above is the interim
  procedure and the gap is recorded.
- Adding a composed `.specify/templates/implementation-template.md` surface was rejected because Spec
  Kit does not produce one; the template is verified through the public resolver instead.
- Relaxing Docusaurus's `onBrokenLinks` to a warning was rejected in favour of `pathname://` view
  links so broken references keep failing the build.
