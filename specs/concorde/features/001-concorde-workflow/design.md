# Feature Design Reference: Concorde Workflow

**Feature**: `feature.concorde.workflow`

**Realization status**: Accepted realization of the architecture-aware Spec Kit workflow under the three-tier feature document model — a self-contained feature TL;DR (`tldr.md`), the complete specification (`spec.md`), and this feature design reference (`design.md`, the accepted realization and full implementation detail) at every feature root, paired with the module summary (`module.md`) and module design reference (`design.md`) at every module — on Architecture Source Profile 3, Feature Workspace Protocol v5, hardening proposal v3, and Build Manifest v6. Hardened 2026-08-28 from the attempt that realized the TL;DR tier and renamed the feature-root accepted realization from `implementation.md` to `design.md`; it supersedes the 2026-08-27 realization, which described the two-document model.

## Realization Overview

Concorde preserves Spec Kit as the owner of specification, clarification, planning, tasks, implementation, analysis, convergence, and task-to-issue conversion. Around that lifecycle it adds reviewed module ownership, feature placement, one optional level of first-class sub-features, selected-workspace routing, bounded context built from module summaries and feature TL;DRs, deterministic validation (structure, contracts, scenarios, evidence, freshness, summary shape and budget, TL;DR shape and budget, reference presence, and the feature-root durable trio), feature-owned diagrams, approval-gated hardening, and a source-grounded read-only question surface.

Every level separates what is read from what is consulted. A module owns `module.md` (the eight-section summary linking its level view and its reference), `design.md` (the module design reference: implementation notes, rationale, alternatives, decision log), and, for a non-leaf, `architecture.json`. A feature root — a top-level feature at `features/<number-name>/` or one immediate sub-feature at `features/<number-name>/subfeatures/<number-name>/` — owns the durable trio `tldr.md`, `spec.md`, and `design.md`, optional `contracts/` and `diagrams/`, and at most one `implementation/` attempt. The TL;DR is the feature's read-first page: self-contained, exactly the five sections `Purpose`, `Functionality`, `Structure`, `Logic`, `Read Next`, within a 3,000-word budget, authored by the specify phase and kept current by clarification, summarizing `spec.md` and never defining beyond it. `spec.md` is the self-contained behavioral authority. This document is consulted when writing the code or fixing a bug: it starts as the `design-template` placeholder seeded by the specify phase, is written in full by the first approved hardening, and is completed by each later one. `design.md` therefore means "design reference" at every level; a feature-root `implementation.md` is a legacy artifact that validation and workspace resolution reject, and no alias or symlink stands in for any of the three names.

Selection remains the standard Spec Kit `.specify/feature.json` pointer (or `SPECIFY_FEATURE_DIRECTORY`). Feature Workspace Protocol v5 derives the selected kind, ID, providing module, `feature_tldr`, `feature_spec`, `feature_design`, the providing module's `module_summary` and `module_design` as navigation references, temporal paths, `implementation_state`, nullable parent context (whose durable trio uses the same three names), and bounded sibling summaries that carry each sibling's `tldr` and `design` paths but never a body. No parallel registry or second feature lifecycle exists.

## Scenario Realization

### Establish and navigate bounded architecture

`speckit.concorde.init` proposes and, after explicit approval, atomically creates four files: `.concorde/config.json` (`profile_version: 3`), `module.md` in the summary shape, a seeded `design.md` stating that nothing has been recorded yet, and `architecture.json`; re-running against the same package returns `unchanged`, and a summary without a reference (or the reverse) is a `conflict`. `speckit.concorde.context` builds one level from the module summary, level view, contracts, and feature summary fields (ID, title, outcome, evidence status, canonical root, `tldr`, `design`); it returns every `design.md`, module or feature, only as a path. A parent feature returns authored-order child summaries; a child returns its parent summary and concise siblings; the parent's `design.md` joins the artifact list only as a path; no body, sibling body, third level, grandchild, or attempt is expanded.

### Place, decompose, select, and specify work

A new root is created by the normal specify phase with `SPECIFY_FEATURE_DIRECTORY` at its canonical path. The preset's specify override resolves `spec-template`, `tldr-template`, and `design-template`; writes `spec.md`; authors `tldr.md` from the same description in the five-section shape (structure link or ```text sketch, `Logic` rules ending with the `FR-NNN` identifiers they summarize); seeds `design.md` only when absent and never creates an `implementation.md`; persists the root to `.specify/feature.json`; and adds three TL;DR items to the spec-quality checklist. The clarify override re-reads the TL;DR after each accepted answer and updates whatever it summarized; the checklist override treats the TL;DR as in scope. Before every normal phase the adapter resolves the selection: a root that still holds `implementation.md` is rejected with a rename remediation, a root holding both names is rejected as ambiguous, a root without `design.md` or without `tldr.md` is rejected with an authoring remediation, and a non-empty attempt is reported as `implementation_state: active`. Validation enforces the same trio deterministically (`CONCORDE-LAYOUT-005` missing `design.md`, `-007` legacy `implementation.md`, `-008` both names, `-009` missing `tldr.md`, and the selection check `-004`) together with the TL;DR rules (`CONCORDE-TLDR-001` section shape, `-002` structure link or sketch, `-003` `Logic` citations, `-004` reading budget as a warning), registration, canonical path, two-level containment, and identity rules.

### Review, implement, validate, and publish

Planning reads `spec.md` and this design reference as the durable inputs, uses the TL;DR for orientation only, uses the level's `module.md` as bounded context, treats the placeholder as no baseline, and consults the module `design.md` only for a specific recorded detail, citing it. Execution, analysis, and convergence record discoveries inside the attempt so hardening can carry them forward; analysis additionally reports any TL;DR statement that `spec.md` does not support, naming the prevailing requirement; none of them writes `tldr.md`, `spec.md`, `design.md`, or a module `module.md`/`design.md`. Validation checks every summary (`CONCORDE-SUMMARY-001..005`, `CONCORDE-MODULE-002`) and every TL;DR, and repeated runs over unchanged sources are byte-equivalent. Publication opens each feature on its TL;DR with the core diagram embedded, offers the specification and the design reference as companion pages, renders each module summary with its level view embedded and its reference linked, rewrites a summary's view link to the delivered route with `pathname://`, and excludes every attempt; a legacy `implementation.md`, a `spec.md` without `tldr.md`, and an unpaired `design.md` or `tldr.md` are publication errors.

### Ask about Concorde

The installed `ask` surface grounds answers in installed extension/preset guidance, module summaries, and feature TL;DRs first. It opens a feature `spec.md` only when a requirement's exact wording is needed and a module or feature `design.md` only when the question asks for implementation detail, rationale, or accepted realization, cites each file it opens, distinguishes summary, TL;DR, required behavior, design reference, attempt, generated evidence, containment, and refinement, and never invokes a runtime operation or mutates the workspace.

### Harden one selected lifecycle root

Proposal mode resolves the selected parent or child, requires at least one recognizable task and every task and existing checklist item to be complete and well formed, and returns `proposal_path`, task and checklist summaries, the workspace (including `feature_tldr`, `feature_design`, `module_summary`, and `module_design`), and a `source_digest` that covers the current `tldr.md`, feature `design.md`, and module `design.md`. The agent drafts the candidate feature `design.md` under the six required headings (further implementation-detail headings may follow) and, when the attempt produced module-level detail or rationale, a full replacement of the providing module's `design.md`. Apply accepts proposal v3 only: `design.path` must equal `feature_design` (a path naming `tldr.md`, `spec.md`, `module.md`, or `implementation.md` is `invalid`), an optional `module_design.path` must equal `module_design` (an amendment naming `module.md`, another level's `design.md`, or a path inside the feature root is `invalid`), and `remove` must be exactly the attempt directory. It re-resolves every path, relationship, task, checklist, symlink, and digest, stages `.design.md.concorde-stage` beside each target, backs up the originals, moves the attempt aside, promotes every staged file, and on any failure restores every backup and the attempt. The result reports `design_digest_before/after`, `module_design_digest_before/after` (null when not amended), removed artifacts, and retained authorities: the selected `tldr.md` and `spec.md`, the module summary, the parent trio, and sibling trios, all byte-identical.

## Durable Implementation Decisions

- `design.md` is the design reference at every level; a feature-root `implementation.md` is legacy, and no compatibility alias, symlink, or transition period exists because Concorde is the only adopter (one-time refactor of this repository).
- The feature TL;DR is an authored, self-contained document with exactly the five sections in order, a structure link (declared diagram, level view, delivered `/architecture/*.html` route) or a fenced text sketch, `Logic` citations resolving to `**FR-NNN**` definitions in the adjacent `spec.md`, and a 3,000-word budget reported as a warning; it is written by specification and clarification only and never by hardening, and where it disagrees with `spec.md` the specification prevails and analysis reports the disagreement.
- `CONCORDE-TLDR-003` fires on an unknown citation, or on no citation when the specification defines at least one `**FR-NNN**`; specifications that number requirements differently produce no citation finding.
- Feature Workspace Protocol v5 is a closed schema (`feature_tldr`, `feature_design`, `module_summary`, `module_design`, `design_digest_*`, `module_design_digest_*`); the hardening proposal is v3; Architecture Source Profile 3 has no Profile 2 reader; Architecture Service Protocol stays v1 with additive fields; Build Manifest is v6.
- The accepted realization is seeded as a placeholder at specification, written in full by the first hardening, completed by later ones, keeps the six required headings first, and rejects the placeholder marker as candidate content.
- Hardening promotes an ordered set of staged files and the attempt removal atomically with full rollback; the source digest binds `tldr.md` and both design references so a manual edit between review and apply is a `conflict`.
- The preset carries five templates; `tldr-template` and `design-template` are verified through the public preset resolver and have no composed mirror; the bash helpers export `FEATURE_TLDR` and `FEATURE_DESIGN`.
- Documentation routes are owned by the content registry and injected as `slug` front matter into the staged copies: the TL;DR takes the route the specification used to own, the specification `…/spec`, the design reference `…/design`; feature-root contract documents (`contracts/<name>.md`, schemas) are not published, so TL;DRs name them as code spans rather than links.
- Self-hosted mirrors are regenerated through feature 004's codex-only tooling by setting both host integration records to codex (skills mode), running `propose` → `apply --proposal .specify/self-hosting-proposal.json` → `status --require-current`, backing up the regenerated codex skills, restoring the `claude` records, re-materializing the `claude` skills through `preset remove` + `preset add --dev` and `extension add --dev --force`, and restoring the codex skills; `.claude/skills` contains symlinks into `.agents/skills`, so it is regenerated rather than copied.
- The single core diagram remains an Archify `architecture` view whose intent node reads `tldr.md + spec.md` and whose reference node reads `Feature Design Reference / design.md`; notes stay within Archify's 140-character limit.
- Preset, extension, bundle, and docsite generator sources are 0.3.0 and release fixtures follow; the published catalogs are not rewritten ahead of a release.

## Known Limitations

- The first-time-maintainer comprehension pilot (SC-005) and the human placement, mental-model, and hardening-comprehension studies remain pending; automated evidence does not substitute for them.
- Browser containment and light/dark perceptual review of the delivered views remain pending because Chrome/Chromium is unavailable; showcase validation does not establish visual polish.
- The self-hosting tooling (feature 004) recognizes only the codex integration; under this checkout's active `claude` integration its `status` reports `unknown`.
- The three leaf modules record a `Structure` rationale instead of a level view; authoring their views is deferred.
- Other roots' design references were renamed and retitled only; their prose still describes the previous model, feature 003's diagrams still label the 0.1.0 inventory, and the five module-level feature specifications number their requirements without `**FR-NNN**` identifiers, so their TL;DRs cite by section.
- The documentation site does not publish feature-root contract documents (`contracts/<name>.md`, schemas); widening that set is feature 002 scope.
- Compatibility is bounded to Spec Kit 0.16.4; deterministic validation cannot prove that a TL;DR or summary is well written or faithful, and the reading-budget proxies are advisory.
- The constitution's A.III relaxation of one providing module per feature remains a separately tracked follow-up; Protocol v5 still reports one `providing_module`.

## Implementation Detail

### Runtime

- `repository.py`: `load_config` accepts only `profile_version == 3`; `load` discovers, for each module, `<module>/design.md`, and, for each feature root, `tldr.md` and `design.md`, reading them into `package.auxiliary` and appending them to the digest artifact list; attempt files under `implementation/` remain auxiliary but outside the digest.
- `feature_workspace.py`: `WorkspacePaths` carries `feature_tldr`, `feature_spec`, `feature_design`; `resolve_phase_paths` checks, in order, the canonical `spec.md`, the ambiguous pair, the legacy `implementation.md`, the missing `design.md`, and the missing `tldr.md`, each raising `WorkspaceError` with the remediation in the message; `_summary()` returns `tldr` and `design`; parent context carries the trio; `resolve_planned_phase_paths` returns the same fields for a not-yet-specified root.
- `validation/tldr.py`: `REQUIRED_TLDR_SECTIONS`, `TLDR_BUDGET_WORDS = 3000`; H2 headings are read outside fenced blocks; `Structure` is satisfied by a link resolving (relative to the TL;DR or project-relative) to a declared diagram source, the feature's `architecture_view`, any maintained view or diagram, an `<a href="/architecture/…html">` route, or a fenced ```text block; `Logic` citations are `FR-\d{3}` tokens compared with `**FR-NNN**` definitions in the feature body; the budget reuses `body_words()` from `validation/summary.py`; a missing `tldr.md` is left to `validation/layout.py` (`CONCORDE-LAYOUT-009`).
- `validation/layout.py`: the trio checks run per feature root; `.specify/feature.json` is rejected (`CONCORDE-LAYOUT-004`) when the selected root holds `implementation.md` or lacks any of the three files.
- `feature_hardening.py`: `_hardening_digest` includes `feature_tldr`, `feature_design`, and `module_design`; proposal mode lists `tldr.md` among the artifacts; apply rejects `proposal_version != 3`, any `implementation` key, and a `design.path` other than `feature_design` (with a dedicated message for `tldr.md`, `spec.md`, `module.md`, and `implementation.md`); `_amendment_target` rejects `module.md` and any path inside the feature root; retained artifacts are the selected `tldr.md` and `spec.md`, the module summary, the unamended module reference, the parent trio, and sibling trios.
- `diagnostics.py` and `scripts/python/workspace.py` emit `schema_version: 5`; `initialize.py` seeds `profile_version: 3`.
