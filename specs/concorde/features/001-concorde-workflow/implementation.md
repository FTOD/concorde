# Feature Implementation: Concorde Workflow

**Feature**: `feature.concorde.workflow`

**Realization status**: Accepted realization of the architecture-aware Spec Kit workflow under the two-document model — a module summary (`module.md`) paired with a module design reference (`design.md`), and a feature specification (`spec.md`) paired with an accepted realization (`implementation.md`) — on Architecture Source Profile 2, Feature Workspace Protocol v4, hardening proposal v2, and Build Manifest v5. Hardened 2026-08-27 from the attempt that realized the document model; it supersedes the 2026-08-26 realization, which described the previous model.

## Realization Overview

Concorde preserves Spec Kit as the owner of specification, clarification, planning, tasks, implementation, analysis, convergence, and task-to-issue conversion. Around that lifecycle it adds reviewed module ownership, feature placement, one optional level of first-class sub-features, selected-workspace routing, bounded context built from module summaries, deterministic validation (structure, contracts, scenarios, evidence, freshness, and now summary shape, reading budget, reference presence, and feature-root document pairing), feature-owned diagrams, approval-gated hardening, and a source-grounded read-only question surface.

Every level separates a summary that is read from a reference that is consulted. A module owns `module.md` (responsibility, boundary, a `Structure` section linking its level view or recording a leaf rationale, inventory tables for features, contracts, and submodules, one representative scenario, and a short design rationale that links `design.md`), `design.md` (implementation detail and the ideas, rationales, alternatives, and decisions developed during development, organized under stable headings and never an implicit input to any operation), and, for a non-leaf, `architecture.json`. A lifecycle root is either a top-level feature at `features/<number-name>/` or one immediate sub-feature at `features/<number-name>/subfeatures/<number-name>/`; both own `spec.md`, `implementation.md`, optional contracts and diagrams, and at most one `implementation/` attempt. `design.md` is reserved for modules and `implementation.md` for feature roots; a feature-root `design.md` is a legacy artifact, and no alias or symlink may stand in for either name.

The accepted realization starts as a placeholder seeded by the specify phase from the preset's `implementation-template` (a placeholder stating only that nothing is hardened yet); the first approved hardening overwrites it in full and each later hardening completes it. Planning treats the placeholder as the absence of a baseline. The same approved hardening may amend the providing module's `design.md`; nothing else in the workflow writes a module reference, while maintainers may edit one directly as an ordinary maintained source.

Selection remains the standard Spec Kit `.specify/feature.json` pointer (or `SPECIFY_FEATURE_DIRECTORY`). Feature Workspace Protocol v4 derives the selected kind, ID, providing module, `feature_spec`, `feature_implementation`, the providing module's `module_summary` and `module_design` as navigation references, temporal paths, `implementation_state`, nullable parent context (whose durable pair is `feature_spec`/`feature_implementation`), and bounded sibling summaries that carry each sibling's `implementation` path but never a body. No parallel registry or second feature lifecycle exists.

## Scenario Realization

### Establish and navigate bounded architecture

`speckit.concorde.init` proposes and, after explicit approval, atomically creates four files: `.concorde/config.json` (`profile_version: 2`), `module.md` in the summary shape (its `Structure` links `architecture.json`, its inventories read `None.`, its representative scenario names the seeded root-overview scenario, and its `Design Rationale` links `design.md`), a seeded `design.md` stating that nothing has been recorded yet, and `architecture.json`. Re-running against the same package returns `unchanged`; a target holding a summary without a reference, or the reverse, is a `conflict`. `speckit.concorde.context` builds one level from the module summary, level view, contracts, and feature summaries; it returns `design.md` and every feature's `implementation.md` only as paths. A parent feature returns authored-order child summaries; a child returns its parent summary and concise siblings; no reference or realization body, sibling body, third level, grandchild, or attempt is expanded.

### Place, decompose, select, and specify work

A new root is created by the normal specify phase with `SPECIFY_FEATURE_DIRECTORY` at its canonical path; the preset's specify override resolves `implementation-template`, seeds `spec.md` and the placeholder `implementation.md`, never creates a feature-root `design.md`, preserves an existing `implementation.md` byte-for-byte, and persists the root to `.specify/feature.json`. Before every normal phase the adapter resolves the selection: a root whose accepted realization still bears the legacy name is rejected with a rename remediation, a root holding both names is rejected as ambiguous, and a non-empty attempt is reported as `implementation_state: active`. Validation enforces the same pairing deterministically (`CONCORDE-LAYOUT-005` missing `implementation.md`, `-007` legacy `design.md`, `-008` both names) together with registration, canonical path, two-level containment, and identity rules.

### Review, implement, validate, and publish

Planning reads `spec.md` and `implementation.md` as the durable inputs, uses the level's `module.md` as bounded architecture context, treats the placeholder as no baseline, and consults the module `design.md` only for a specific recorded detail, citing it. Execution, analysis, and convergence record discoveries inside the attempt so hardening can carry them forward; none of them writes `implementation.md`, `module.md`, or `design.md`. Validation checks every summary for the eight required sections, the view link or leaf rationale, inventory tables or `None.`, and a link resolving to the adjacent reference (`CONCORDE-SUMMARY-001..004`, errors), reports a body over 4,000 words as `CONCORDE-SUMMARY-005` (warning; status unchanged), and requires a real non-empty `design.md` beside every summary (`CONCORDE-MODULE-002`). Repeated runs over unchanged sources are byte-equivalent. Publication renders each module summary with its level view embedded, links the reference page, pairs each specification with its implementation page, rewrites a summary's view link to the delivered view route with Docusaurus's `pathname://` protocol, and excludes every attempt.

### Ask about Concorde

The installed `ask` surface grounds answers in installed extension/preset guidance and module summaries first. It opens a module `design.md` or a feature `implementation.md` only when the question asks for implementation detail, rationale, or accepted realization, cites each file it opens, distinguishes summary, reference, required behavior, accepted realization, attempt, generated evidence, containment, and refinement, and never invokes a runtime operation or mutates the workspace.

### Harden one selected lifecycle root

Proposal mode resolves the selected parent or child, requires at least one recognizable task, requires every task and existing checklist item to be complete and well formed, and returns `proposal_path`, task and checklist summaries, the workspace (including `feature_implementation`, `module_summary`, and `module_design`), and a `source_digest` that covers the current module `design.md`. The agent drafts the candidate `implementation.md` under the six required headings and, when the attempt produced module-level detail or rationale, a full replacement of the providing module's `design.md`. Apply accepts proposal v2 only: `implementation.path` must equal `feature_implementation`, an optional `module_design.path` must equal `module_design` (an amendment naming `module.md`, another level's `design.md`, or a feature-root `design.md` is `invalid`), and `remove` must be exactly the attempt directory. It re-resolves every path, relationship, task, checklist, symlink, and digest, stages `.implementation.md.concorde-stage` and, when proposed, `.design.md.concorde-stage`, backs up the originals, moves the attempt aside, promotes every staged file, and on any failure restores every backup and the attempt. The result reports `implementation_digest_before/after`, `module_design_digest_before/after` (null when not amended), removed artifacts, and retained authorities including the module summary, the parent pair, and sibling pairs, all byte-identical.

## Durable Implementation Decisions

- The name `design.md` belongs to modules and `implementation.md` to feature roots; the legacy feature-root name is invalid, and no compatibility alias, symlink, or transition period exists because Concorde is currently the only adopter (one-time refactor of this repository).
- The module summary shape is eight fixed H2 sections with a deterministic structure rule (link to the declared view, or non-empty rationale for a leaf without a view), inventory tables or the literal `None.`, and a reachable reference link; the reading budget is 4,000 body words (front matter, fenced code, and HTML comments excluded) reported as a warning.
- The module design reference carries no front matter or ID, contains an H1 and at least one H2, may be a seeded placeholder, is included in the package source digest, is returned by context and workspace results only as a path, and is written by the workflow only through an approved hardening proposal as full replacement content.
- The accepted realization is seeded as a placeholder at specification, written in full by the first hardening, completed by later ones, keeps the six required headings, and rejects the placeholder marker as candidate content.
- Feature Workspace Protocol v4 is a closed schema (`feature_implementation`, `module_summary`, `module_design`, `implementation_digest_*`, `module_design_digest_*`); the hardening proposal is v2; Architecture Source Profile 2 has no Profile 1 reader; Architecture Service Protocol stays v1 with additive fields; Build Manifest is v5.
- Hardening promotes an ordered set of staged files and the attempt removal atomically with full rollback; the source digest binds the module reference so a manual edit between review and apply is a `conflict`.
- Spec Kit 0.16.4 composes only its core template names; the `implementation-template` is verified through the public preset resolver and has no composed mirror, and the stale `design-template` mirror was removed.
- Self-hosted mirrors are regenerated through feature 004's codex-only tooling by temporarily setting both host integration records to codex (skills mode), then restoring the `claude` records and re-materializing its skills; the self-host digest ignores Spec Kit's `.specify-dev/` dev-install cache, which is git-ignored.
- The documentation content plugin rewrites a summary's declared view link to the delivered route using `pathname://` so Docusaurus's route-only broken-link check accepts the static file; Docusaurus's persistent bundler cache must be cleared after plugin edits.
- The single core diagram remains an Archify `architecture` view showing five surfaces and four runtime operations; module view notes stay within Archify's 140-character limit.
- Preset, extension, and bundle sources are 0.2.0 and release fixtures follow; the published catalogs are not rewritten ahead of a release.

## Known Limitations

- The first-time-maintainer comprehension pilot (SC-004) and the human placement, mental-model, and hardening-comprehension studies remain pending; automated evidence does not substitute for them.
- Browser containment and light/dark perceptual review of the delivered views remain pending because Chrome/Chromium is unavailable; showcase validation does not establish visual polish.
- The self-hosting tooling (feature 004) recognizes only the codex integration; under this checkout's active `claude` integration its `status` reports `unknown`, exactly as before this attempt.
- The three leaf modules (`architecture-core`, `distribution`, `spec-kit-integration`) record a `Structure` rationale instead of a level view; authoring their views is deferred.
- Other roots' accepted realizations were renamed only; their prose still describes the previous model, and feature 003's diagrams still label the 0.1.0 inventory, until their own attempts are hardened.
- Compatibility is bounded to Spec Kit 0.16.4; deterministic validation cannot prove that summaries are well written, and the reading-budget proxy is advisory.
- The constitution's A.III relaxation of one providing module per feature remains a separately tracked follow-up; Protocol v4 still reports one `providing_module`.
