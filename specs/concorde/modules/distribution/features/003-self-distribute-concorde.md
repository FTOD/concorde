# Feature Design: Self-Distribute Concorde Into Its Source Checkout

## Outcome and Scope

A Concorde maintainer can check or refresh this repository's generated Codex and Claude public-leaf,
Operation, and internal reflection-agent surfaces directly from canonical sources while both internal
planner leaves remain package-only. Status, enforcement, and apply operate against one explicit
source worktree, never another worktree's projections. Repository-level agent policy detects when a
conversation's project-local Skill path belongs to a different worktree and requires the user to
open a new agent in the target worktree. Generated Skill bodies remain ordinary canonical
projections with no self-hosting text injected into them.

## Usage

From the worktree being maintained, run:

```bash
python3 scripts/development/sync-agent-surfaces.py status --project-root .
python3 scripts/development/sync-agent-surfaces.py check --project-root .
python3 scripts/development/sync-agent-surfaces.py apply --project-root .
```

`status` reports drift without failing, `check` returns nonzero on any drift, and `apply` replaces
only the exact generated outputs in that same worktree. To validate an agent session, pass an
absolute project-local Skill path exactly as advertised by its runtime:

```bash
python3 scripts/development/sync-agent-surfaces.py verify-worktree \
  --project-root . \
  --loaded-skill-path /absolute/runtime/path/to/concorde-ask/SKILL.md
```

If the loaded path belongs to another worktree, stop and ask the user to open an agent in the target
worktree. Do not sync the old/primary worktree as a substitute.

## Interfaces

### `interface.concorde.source-checkout-distribution` — Worktree-local self-distribution

- **Consumer**: Concorde maintainer, source-checkout agent, and PR CI.
- **Direction**: One worktree's canonical package sources to that same worktree's agent projections,
  freshness result, and agent/worktree affinity result.
- **Entry points**: `scripts/development/sync-agent-surfaces.py
  status|check|apply [--format json]`; and `verify-worktree --project-root .
  --loaded-skill-path <absolute-runtime-advertised-path>`.
- **Inputs**: Root 17-leaf sources with exposure/effects, three paired Operations, reflection assets,
  both integration renderers, observed generated paths, and for affinity verification one absolute
  loaded project Skill path.
- **Outputs**: Capability-surface status schema 2 with `tool`, output count, and sorted
  action/path/digest entries; refreshed regular files on apply; or worktree-affinity result schema 1
  identifying the active/loaded roots, Git HEAD, integration, capability, and surface equality.
- **Obligations**: Render both integrations from the same sources, filter internal leaves, preserve
  target→kind ownership (including plan Skill→Operation transition), use checkout runtime paths,
  replace legacy generated symlinks, never modify canonical inputs, and never add source-checkout
  policy text to generated Skill bodies. Every mode MUST execute from the same worktree named by
  `--project-root`. Affinity verification MUST derive the loaded worktree and
  integration from the exact absolute Skill path, require the active projections to be current, and
  reject every different worktree even when its generated bytes happen to match.
- **Failures**: Invalid Skill/Operation/asset source, missing pair, output collision, or non-file
  target conflict returns failure without a false current status. `check` returns nonzero for any
  create/update/replace-symlink/conflict/unexpected action. An unsafe/non-project loaded path,
  checker/root mismatch, stale active projection, or different loaded/active worktree returns
  nonzero; a worktree mismatch directs the user to open a new agent in the active target rather than
  modifying the Skill-owning worktree.
- **Compatibility**: Package Manifest 2 uses stable `concorde-*` capability names and distinguishes
  `kind: skill` from `kind: operation`; retired dotted identities are not aliases. `status` retains
  its reporting exit behavior, while the new `check` command owns CI failure semantics. Projection
  remains the same for primary worktrees, linked worktrees, and installed projects apart from their
  existing path/integration metadata.
- **Example**: Status reports 40 outputs: 18 public capabilities per integration plus four specialist
  agents.
- **Implementing entities**: `entity.distribution.checkout-sync`,
  `entity.distribution.source-agent-policy`, `entity.distribution.codex-checkout-surface`,
  `entity.distribution.claude-agent-policy-shim`,
  `entity.distribution.claude-checkout-surface`, `entity.distribution.source-checkout-ci`,
  `module.concorde.capabilities`, and `module.concorde.reflections`.

  semantics that this checkout sync reuses.
- `feature.distribution.package-concorde` defines the canonical package inventory that self-
  distribution projects without installing a duplicate framework.
- `feature.lifecycle.standard-development-loop` provides one paired graph whose projection this sync

  own isolated worktree before a newly opened agent can use them.

## User Scenarios & Testing

### User Story 1 — Detect Drift (Priority: P1)

**Independent Test**: Modify one generated skill, run status, and observe its exact `update` action
without source mutation.

1. **Given** current projections, **When** status runs, **Then** every action is `current`.
2. **Given** a missing, stale, or legacy symlink output, **When** status runs, **Then** it reports
   `create`, `update`, or `replace-symlink` for that exact path.

### User Story 2 — Refresh Both Integrations (Priority: P2)

**Independent Test**: Apply from drift and prove all capability/reflection-agent outputs match render
results.

1. **Given** conflict-free generated paths, **When** apply runs, **Then** Codex and Claude surfaces
   become byte-current and no root source changes.

### User Story 3 — Enforce Freshness in Pull Requests (Priority: P1)

**Independent Test**: Change one canonical Skill without applying its projections and run `check`.

1. **Given** current projections, **When** `check` runs, **Then** it exits zero with `current`.
2. **Given** any projection drift, **When** `check` runs, **Then** it exits nonzero without mutation.
3. **Given** a pull request, **When** source-checkout CI runs, **Then** it requires `check` and the
   projection/worktree-affinity contract tests to pass.

### User Story 4 — Reject Skills Loaded From Another Worktree (Priority: P1)

**Independent Test**: Start with a Skill path in a primary checkout, create a linked worktree, and
run that linked worktree's verifier with the primary path.

1. **Given** the loaded Skill and active project belong to the same current worktree, **When**
   verification runs, **Then** it reports `current`.
2. **Given** the paths belong to different worktrees, **When** verification runs, **Then** it exits
   nonzero even when their generated Skill bytes match and explicitly asks the user to open a new
   agent in the active worktree.
3. **Given** canonical Skills change in the linked worktree, **When** its own `apply` runs, **Then**
   only that linked worktree is refreshed; a verifier carrying a primary Skill path still rejects,
   while one carrying the linked-worktree path succeeds.

## Requirements

- **FR-001**: Root `skills/`, `operations/`, and agent-asset sources MUST be the only capability/role
  content inputs; checkout sync MUST NOT inject repository policy into generated Skill bodies.
- **FR-002**: Status MUST classify current/create/update/replace-symlink/conflict/unexpected without
  mutation; an unexpected project-owned projection name remains untouched but prevents `check` and
  `apply` from reporting current.
- **FR-003**: Apply MUST write regular files for both integrations and remove no unrelated agent asset.
- **FR-004**: Generated skills MUST contain no unresolved package tokens or host-owned paths.
- **FR-005**: A second status after apply MUST be `current`.
- **FR-006**: Internal leaves MUST have no desired output and the public `concorde-plan` target MUST
  carry `kind: operation`/entry-point provenance in both integrations.
- **FR-007**: `check` MUST preserve the status schema and read-only behavior but return nonzero when
  any desired output is not current.
- **FR-008**: Every sync mode MUST reject a `--project-root` different from the worktree containing
  the invoked sync script.
- **FR-009**: `verify-worktree` MUST accept only an absolute regular project-local
  `.agents/skills/concorde-*/SKILL.md` or `.claude/skills/concorde-*/SKILL.md`, derive its Git root and
  integration, compare generated capability manifests, and reject every loaded/active root mismatch.
- **FR-010**: The repository's Codex/Claude project policy MUST require verification before work,
  forbid continuing into a worktree created by the current session, and direct the user to open a
  new agent in the target worktree on failure.
- **FR-011**: The same policy MUST require canonical Skill changes to run `apply` and `check` from
  their own primary or linked worktree, never update another worktree, and prohibit an already-loaded
  project Skill from governing maintenance of its own surface.
- **FR-012**: Pull-request CI MUST run `check` plus the source projection and worktree-affinity
  contract tests.

## Success Criteria

- **SC-001**: Both integration projections are reproducible from root sources in one shell invocation.
- **SC-002**: No canonical package directory is duplicated beneath `.concorde` in this checkout.
- **SC-003**: Each integration has exactly 18 public capabilities; total maintained checkout output is 40.
- **SC-004**: Projection drift cannot pass `check` or the pull-request source-checkout job.
- **SC-005**: A primary-loaded agent cannot work in a linked worktree, while a newly opened agent
  whose Skill path belongs to that linked worktree can verify and use its locally synchronized Skills.

## Edge Cases

- A stale generated Skill is a symlink into a removed package directory.
- A desired output path exists as a directory and therefore cannot be replaced safely.
- Two worktrees currently have byte-identical generated Skills; identity still differs and the old
  agent must be reopened in the target.
- A linked worktree changes a canonical Skill but has not applied projections; both `check` and
  affinity verification reject its stale active surface.
- A maintainer invokes the primary worktree's sync script with a linked `--project-root`, or the
  reverse; worktree-local enforcement rejects the command before mutation.
